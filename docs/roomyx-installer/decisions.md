# roomyx-installer — Decisions

Version: 0.1.0

Формат по конвенции keryx (`docs/requirements/keryx-mcp-client/decisions.md`) и уже применённый в `roomyx/decisions.md`. Нумерация локальна для этого пакета.

## D-01: `roomyx init` — явная команда, не npm postinstall-хук

**Решение.** `.roomyx/` создаётся только явным вызовом `roomyx init`, никогда автоматически при `npm install`.

**Причина.** npm postinstall-скрипты, которые пишут файлы в проект пользователя без явного действия, — известный источник недоверия к пакету (и реальный вектор supply-chain проблем в экосистеме в целом). keryx уже решил этот вопрос именно так — `npm install` ставит бинарник, `keryx init` — отдельный, осознанный шаг, который явно печатает, что именно будет создано. Повторяем то же самое для консистентности и безопасности, а не изобретаем новый паттерн.

## D-02: Синхронизация с реальным `~/.claude/skills/...` — отдельное, явно подтверждаемое действие

**Решение.** Механизм `skills sync` полностью реализуется и тестируется против фикстур/временных директорий. Запуск синхронизации против настоящего `~/.claude/skills/startup-room/SKILL.md` (или аналогов `.codex`/`.keryx`) требует отдельного подтверждения оператора в момент запуска — не является автоматическим следствием того, что механизм реализован.

**Причина.** `~/.claude/skills/startup-room/SKILL.md` — не игрушечный файл: это тот самый скилл, который вёл всю методологию startup-room в этой же сессии, включая мета-ревью самого себя и все последующие правки. Автоматическая перезапись без отдельного, осознанного шага рискует молча потерять доработки, которые не попали в бандл. Это тот же принцип, что уже применялся в этой сессии для `git push --force` и `npm publish` — необратимые или трудно обратимые действия против реальных, разделяемых артефактов получают отдельную точку подтверждения, а не проскакивают как побочный эффект реализации фичи.

**Отвергнутая альтернатива.** Автоматическая синхронизация при каждом `roomyx init`/обновлении пакета. Отклонено: это ровно тот сценарий, который D-02 существует чтобы предотвратить — тихая перезапись живого, дорабатываемого вручную файла.

## D-03: Реестр комнат проверяется по факту жизни процесса, не только по наличию записи

**Решение.** `roomyx client`'s авто-подключение выполняет реальную проверку живости (лёгкий MCP-вызов) перед тем, как довериться записи реестра; протухшие записи (от упавших процессов) удаляются из реестра, а не остаются висеть.

**Причина.** Реестр — обычный JSON-файл, который переживает падение процесса, если тот не успел выполниться `SIGTERM`-обработчик (`kill -9`, падение хоста и т.д.). Без проверки живости "одна команда — и ты в комнате" превратилась бы в "одна команда — и уверенное подключение в никуда", что хуже явной ошибки.

## D-04: `npm publish` — вне объёма реализации, отдельное решение

**Статус: решение принято, пакет опубликован 2026-09-09.** `"private": true` снят, `0.1.0` вышел под разовым granular-токеном с обходом 2FA (classic Automation-токенов у npm больше нет), после чего зарегистрирован trusted publishing и токен отозван. Дальнейшие релизы идут по OIDC-личности воркфлоу, без токенов, с provenance. Один нюанс, стоивший двух неудачных прогонов: trusted publisher по умолчанию разрешает только `npm stage publish`, и прямую публикацию надо явно включить галкой «Allow npm publish» — иначе npm отвечает `403 OIDC permission denied for this action`.

**Исходное решение (сохранено как контекст).** Пакет собирается и готовится к публикации (`package.json` содержит корректные метаданные, но `"private": true` до явного решения). Реальная команда `npm publish` не выполняется как часть реализации этой спеки.

**Причина.** Публикация публичного npm-пакета — действие с ограниченной обратимостью (имя пакета занимается в реестре; npm ограничивает повторную публикацию под тем же именем после unpublish). Это ровно тот класс действий, который по общим рабочим принципам этой сессии требует явного подтверждения в момент выполнения, а не молчаливого выполнения потому что "весь остальной код готов".
