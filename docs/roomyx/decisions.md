# roomyx — Decisions

Version: 0.5.0

Формат по конвенции keryx (`docs/requirements/keryx-mcp-client/decisions.md`): решение + причина + (где применимо) отвергнутая альтернатива. Нумерация локальна для этого пакета.

## D-01: MCP-сервер только читает состояние и принимает команды; лог по-прежнему пишет только диспетчер

**Решение.** `room.post_owner_command` передаёт команду диспетчеру через MCP, но сам сервер никогда не пишет напрямую в append-only лог комнаты.

**Причина.** Вся консистентность startup-room держится на правиле "единственный писатель" (см. находки Омара в мета-ревью фреймворка, `../startup-room-framework/README.md`). Если TUI получит право писать в лог напрямую, comната получит два независимых источника мутаций — ровно тот класс бага (гонка записи), который мета-ревью уже определило как риск. Дешевле держать TUI строго read+propose, никогда write.

## D-02: MCP, не файл-лог, для транспорта TUI↔оркестратор

**Решение.** Выбран MCP-сервер (`prd.md` R2), а не более простой вариант "оркестратор пишет JSON-lines файл, TUI его читает".

**Причина.** Explicit trade-off, обсуждённый с оператором: файл проще (ничего нового не изобретать, лог уже существует), но не даёт естественного места для интерактивных команд (R5) и структурированных per-agent запросов (R4) без надстройки поверх файла, которая по сути реализовала бы половину MCP заново. Оператор выбрал функциональность (модалки + команды) важнее простоты транспорта.

**Отвергнутая альтернатива.** Файл-лог + отдельный, самодельный command-канал (например, второй файл для команд, который диспетчер поллит). Отклонено: два самодельных механизма (чтение состояния + приём команд) добавляют больше сложности, чем один MCP-сервер, и не переиспользуют ничего готового — тогда как MCP-путь напрямую использует паттерн, уже проверенный в keryx (`src/mcp`, `src/tui/mcp-inspector.ts`).

## D-03: Один провайдер на сессию, без смешивания (v1)

**Решение.** Комната наследует ровно тот провайдер/модель, что и её оркестратор. Не поддерживается: Claude-персонаж + внешний DeepSeek/другой-провайдер-персонаж одновременно в одной комнате.

**Причина.** В процессе обсуждения архитектуры (эта переписка, 2026-09-08) рассматривался более сложный вариант — "приглашённые мнения" от внешних провайдеров через `keryx harness run` — и был явно отклонён оператором как избыточная сложность для текущей цели ("давай пока проще"). Зафиксировано здесь, чтобы не переоткрывать тот же вопрос без явного нового запроса.

**Отвергнутая альтернатива.** Смешанные комнаты (Claude-оркестратор + Claude-персонажи + внешний DeepSeek-персонаж через keryx harness). Технически осуществимо (DeepSeek уже настроен как провайдер в keryx, см. переписку), но добавляет: управление историей для stateless `harness run`-вызовов (нет continue/resume, в отличие от `keryx shell`), вопрос утечки данных на сторонний провайдер, и разметку доверия в логе (внешний участник ≠ owner). Отложено, не отменено — может вернуться отдельным пакетом требований, если понадобится.

## D-04: Не обобщать MCP-клиент keryx под "любой оркестратор" в v1

**Решение.** roomyx v1 не трогает и не расширяет `src/mcp-client` в keryx (сегодня заточен только под `codex mcp-server`, решение D-04 в самом `keryx-mcp-client` пакете).

**Причина.** В однопровайдерной модели (D-03) каждый оркестратор поднимает СВОЙ MCP-сервер и не подключается к чужому как клиент — значит roomyx вообще не нуждается в MCP-клиенте keryx для v1. Экономит реальную работу (обобщение узкоспециализированного клиента — нетривиальная задача, см. keryx's D-04 про "generic client is scope creep без второго реального потребителя").

## D-05: Claude как внешний write-capable агент — не решаем, потому что не относится к делу

**Решение.** Ограничение Anthropic (`claude -p`, `--permission-prompt-tool` принудительно отдаёт "deny" на мутирующие действия в неинтерактивном режиме — задокументировано в `keryx-mcp-client/decisions.md` D-01 самого keryx) явно не является блокером для этого пакета и не требует обхода.

**Причина.** roomyx никогда не запускает Claude как внешне управляемого подчинённого агента — Claude-персонажи всегда идут через нативный Agent/SendMessage того же Claude Code инстанса, что ведёт комнату (см. D-03 выше: один провайдер = сам оркестратор). Вендорское ограничение относится к другому сценарию (кто-то ДРУГОЙ спавнит headless Claude и пытается управлять им извне через MCP elicitation) — не заявляем работу над обходом, потому что обходить нечего.

## D-06: Транспорт — Streamable HTTP на loopback, без токена в v1

**Решение.** MCP-сервер и TUI-клиент соединяются через `StreamableHTTPServerTransport`/`StreamableHTTPClientTransport` (`@modelcontextprotocol/sdk`), сервер биндится только к `127.0.0.1` по умолчанию; без токена/авторизации в этой версии.

**Причина.** Изначально предполагался stdio-транспорт (родительский процесс спавнит дочерний), но архитектура сама требует независимых процессов: оркестратор поднимает сервер как часть своей сессии, TUI запускается ОТДЕЛЬНО пользователем в другом терминале (или позже — оркестратором как дочерний процесс, но не гарантированно в одном родительском дереве) — stdio требует общего parent-child pipe, которого здесь нет по дизайну. HTTP loopback — стандартный путь для независимых процессов на одной машине, и прямо соответствует уже существующему в keryx прецеденту `keryx serve` ("loopback-bound HTTP entry... off by default... Bind address. Loopback unless acknowledged"). Отсутствие токена в v1 — осознанное упрощение: угроза ограничена локальной машиной оператора, тем же уровнем доверия, что и у процесса, который сервер запустил; добавление токена/авторизации становится обязательным условием, если/когда roomyx когда-либо перестанет биндиться только на loopback.

**Отвергнутая альтернатива.** stdio-транспорт с TUI-клиентом, спавнящим сервер как свой дочерний процесс (тогда TUI становится "оркестратором" соединения). Отклонено: это меняет модель "оркестратор поднимает сервер" на "TUI поднимает сервер", что противоречит уже согласованному с оператором разделению ролей (комната остаётся полностью во власти оркестратора; TUI — вторичный, необязательный наблюдатель, который можно закрыть/переоткрыть без влияния на саму комнату).

## D-01a: Поправка к D-01 — «единственный писатель» относится к живой комнате, а не к пакету

**Решение.** D-01 ограничивает **сервер**, а не пакет. Инвариант — «один писатель на живую комнату», а не «roomyx никогда не пишет байты». Из этого следует конкретное разделение:

- `roomyx room new <path>` создаёт лог там, где его нет. Диспетчера ещё не существует, число писателей идёт с нуля к одному, гонки нет. Никакого исключения не требуется.
- `roomyx room append <path>` действительно способен нарушить D-01, дописав в лог, который сейчас ведёт диспетчер. Поэтому команда сверяется с реестром и **отказывается**, если этот путь обслуживает живая комната. `--force` перекрывает отказ для того, кто знает, что делает.

**Причина.** До этой поправки единственным способом создать лог комнаты был файл `src/cli/seed.ts`, который отгружается в пакете, но не объявлен в `bin`, не упомянут в README и документирован только в сценарии тестирования — как вызов через абсолютный путь в глобальный `node_modules`. То есть возможность существовала, была недокументированной и всё равно писала в лог. Поправка ничего не добавляет к тому, что пакет уже умеет: она делает это видимым и **ставит охрану там, где охраны не было**.

Формулировка «D-01 ограничивает сервер, а не пакет» — это довод, а не констатация, и поэтому он записан здесь, а не в сообщении коммита. Аргумент, который живёт в переписке, — это слух, а не решение.

**Отвергнутая альтернатива.** Оставить `seed.ts` как есть и не трогать D-01. Отклонено: время до первой комнаты — главное число этого продукта, а инструкция «дотянись до чужого каталога модулей» его не улучшает. И охраны у той записи всё равно не было, то есть отказ от поправки сохранял бы риск, а не устранял его.

## D-06a: Поправка к D-06 — loopback не исключает браузер

**Решение.** Защита от DNS rebinding включена на обоих транспортах: `enableDnsRebindingProtection` вместе с `allowedHosts` и `allowedOrigins`, которые строятся лениво, из фактически занятого порта, внутри создания сессии.

**Причина.** Рассуждение D-06 — «угроза ограничена локальной машиной, тот же уровень доверия, что у процесса, который сервер запустил» — верно для границы между процессами и не выдерживает границы браузера. Страница, которую откроет оператор, не наследует этого доверия и всё равно достучится до 127.0.0.1. Это не новый вид угрозы, а действующее лицо, которое модель угроз D-06 просто не перечислила. Проверено вживую до починки: `initialize` с заголовками `Origin: https://evil.example` и `Host: roomyx.attacker.test` проходил рукопожатие и позволял вызывать инструменты; в связке с тогдашним произвольным путём у `roomyx.skills.sync` это давало запись в файл по выбору атакующего.

Отсутствие токена, о котором D-06 договорился, при этом не пересматривается. Средство здесь — не аутентификация, а три опции, которые SDK уже даёт. Защита останавливает браузер и не останавливает соседний процесс: локальная программа не пошлёт `Origin` вовсе и пройдёт мимо проверки. Это ровно та граница, которую D-06 и провёл, поэтому называть включённую защиту аутентификацией нельзя.

**Две подробности, которые стоили бы дня отладки.** Первая: `allowedHosts` сверяется точным совпадением со всем заголовком `Host`, вместе с портом, — список из голых имён хостов отвечает отказом собственному клиенту roomyx. Вторая: обе проверки нужны одновременно, потому что закрывают разные атаки. Страница на `http://127.0.0.1:<порт>/mcp` шлёт законный `Host`, её останавливает только проверка происхождения; страница после подмены DNS шлёт `Host: attacker.example` и уже одноимённое происхождение, её останавливает только проверка хоста.

**Нижняя граница версии SDK.** Поднята до 1.25.0, и это часть решения, а не гигиена зависимостей. Измерено по тридцати архивам: защита появилась в 1.13.3, но до 1.24.0 она отвергала запросы вовсе без заголовка происхождения — а их шлёт и TUI-клиент, и проверка живости. Проброс опций в тот транспорт, который здесь используется, начинается с 1.25.0. Наивная граница «где защита впервые появилась» заставила бы продукт отвечать отказом самому себе на установках, которые мы не проверяли.

## D-07: Один HTTP-транспорт на оба MCP-сервера

**Решение.** Сессии, привязка к хосту и порту, отказ от не-loopback без явного флага и корректное завершение живут в одном модуле `src/server/http-transport.ts`. И покомнатный сервер (`roomyx serve`), и управляющий (`roomyx mcp`) — тонкие обёртки над ним: каждый задаёт только фабрику `McpServer`, порт по умолчанию и подпись для сообщения об отказе.

**Причина.** Транспорт был написан дважды, и копии успели разойтись: управляющий сервер при остановке не закрывал свои сессии, а покомнатный закрывал. Это не гипотетическое расхождение — оно уже существовало в опубликованном пакете. При двух копиях каждая правка транспортного уровня требует двух одинаковых изменений, и подписанный тарбол — плохое место, чтобы узнать, что второе забыли. Ближайшие работы это подтверждают: включение защиты от DNS rebinding и сборка протухших сессий обе трогают именно транспорт.

Замер перед вынесением: тела двух серверов различались четырьмя содержательными фрагментами (фабрика сервера, подпись в сообщении об отказе, порт по умолчанию, форма опций). Семь тестовых файлов конструируют эти серверы, и **ни один** не импортирует их внутренности — все ходят через `serve()` и `serveManagement()`. Поэтому вынесение, сохраняющее эти две сигнатуры, не потребовало правки ни одного теста. Это проверено, а не предположено.

**Отвергнутая альтернатива.** Оставить две копии и вносить каждую транспортную правку дважды. Отклонено: единственная причина, по которой это работало до сих пор, — что транспорт почти не трогали. Как только его начали трогать, цена дублирования стала реальной, а страховки от пропущенной второй копии в одиночном проекте нет никакой.

## D-08: Контракт лога принадлежит одному модулю, и от него зависят обе стороны

**Решение.** Zod-схемы строки состояния и строки сообщения живут в `src/log/schema.ts`. И читатель (`store.ts`), и писатель (`write.ts`) импортируют их оттуда; ни одна сторона не объявляет свою. `appendMessage` разбирает конверт перед записью, а не после.

**Причина.** Схемы были только на стороне чтения, а у писателя были одни типы TypeScript — которые стираются ровно на границе CLI, где приходит пользовательский ввод: `--kind` приводился к типу через `as never`. Писатель принимал то, что читатель отвергал, по построению. Одна команда `roomyx room append --kind bogus-kind` завершалась успешно, писала строку, и после этого лог не читался **никогда**: он append-only, команды починки нет, а сервер при этом продолжал подниматься и регистрироваться, так что `rooms list` называл комнату живой, а прикреплённый клиент навсегда показывал «отключено» напротив совершенно здорового сервера.

Это не гипотеза: воспроизведено до починки тремя независимыми ревьюерами и оркестратором, и воспроизведено после — три недопустимых вызова отвергаются, в логе остаётся только заголовок.

**Отвергнутая альтернатива.** Проверять только в CLI. Отклонено: `appendMessage` — экспортируемая функция, её вызовет встраивающий диспетчер, и охранник, который можно обойти, не является охранником. Проверка в CLI осталась, но как формулировка сообщения об ошибке, а не как защита: она называет флаг, который человек набрал, а не поле схемы.

## D-09: Ошибка инструмента — не потеря связи, и переподключение одиночное

**Решение.** `callTool` читает `result.isError` и бросает типизированную `ToolError` с текстом сервера. Циклы опроса сообщают о ней и **продолжают опрашивать**: комната достижима. Разрыв транспорта по-прежнему ведёт к `handleDisconnect`, и это разные пути. Переподключение одиночное: счётчик поколений, который каждый цикл захватывает и проверяет, сохранённый дескриптор таймера и закрытие предыдущего клиента.

**Причина.** Ошибка инструмента приходила прозой, на которой спотыкался `JSON.parse`, — неотличимо от обрыва. Оба цикла ловили это независимо, каждый планировал своё переподключение, и каждое стартовало свежую пару циклов, не останавливая работающие: число циклов удваивалось на каждом сбое. Замерено — одна битая строка в логе увела одного клиента в 510 соединений за десять секунд, при живом и отвечающем сервере.

Второй половиной цены был выброшенный текст. Именно он и был диагнозом — «Invalid message line 2 in …», — то есть единственная фраза, которая сказала бы человеку смотреть в лог, а не в сеть. Теперь она попадает в саму ленту, где читается и переживает прокрутку.

**Отвергнутая альтернатива.** Считать любой сбой разрывом и полагаться на переподключение. Отклонено: это и есть исходное поведение, и оно превращает исправимую ошибку данных в неостановимый шторм.

## D-10: Одна дисциплина блокировки — и для реестра, и для самих данных

**Решение.** `withLock` вынесен в `src/lockfile.ts` и используется и реестром комнат, и `appendMessage`. Выделение `seq` и запись строки — одна критическая секция, а не две.

**Причина.** Реестр получил блокировку после трёх раундов ревью — эксклюзивное создание, перехват протухшей по mtime, токен владельца, чтобы медленный держатель не удалил чужую. Комнатный лог, то есть сами данные, не получил ничего. Три параллельных `roomyx room append` выделяли `seq: 1` все три, и все три строки оказывались на диске. `seq` — курсор транскрипта, поэтому клиент, опросивший сервер между двумя столкнувшимися записями, запоминает `sinceSeq = 1` и **никогда** не получает второе сообщение: оно на диске и невидимо в TUI навсегда.

Странность исходного состояния стоит назвать прямо: защищена была бухгалтерия о данных, а не данные.

**Отвергнутая альтернатива.** Написать вторую, более простую блокировку для лога. Отклонено: три раунда закалки существующей — это ровно та работа, которую вторая копия повторила бы с нуля и, скорее всего, не до конца.

## D-11: Сетевая поверхность сообщает, оператор решает

**Решение.** У MCP-инструмента `roomyx.skills.sync` нет ни `yes`, ни `dryRun`. Он сообщает, что синхронизация **сделала бы**. Сам гейт живёт внутри `syncSkill`, считается один раз и по умолчанию закрыт: без явного `yes: true` не пишется ничего.

**Причина.** `yes` — это то, что выключает предохранитель D-02 от затирания. На CLI это нажатие оператора; по сети это булев флаг, который вызывающий ставит себе сам, то есть не предохранитель вовсе. Хуже того, значение по умолчанию считалось на каждой поверхности отдельно, и поверхности разошлись: CLI брал `--dry-run || !yes`, а инструмент передавал оба как `undefined` — поэтому вызов с одним только `target` писал настоящий файл скилла без подтверждения, по неаутентифицированному loopback-порту, в то время как справка самого CLI обещала «без --yes ничего не пишется».

Это то же рассуждение, по которому из этой схемы ранее убрали `targetPath`. Тот проход забрал путь и оставил гейт.

**Отвергнутая альтернатива.** Оставить `yes` и считать loopback достаточной границей. Отклонено: D-06a уже зафиксировала, что loopback не ограничивает браузер, а D-02 существует ровно затем, чтобы появление настоящего файла скилла было осознанным действием, а не побочным эффектом существования механизма.

## D-12: Три пункта отложены — с причинами, а не молчанием

**Решение.** Обработка ресайза терминала, арифметика по ячейкам отображения и `limit` для `room.get_transcript` в исправительный флоу 001 не входят. Все три остаются в отчёте ревью и в разделе Known в CHANGELOG.

**Причина.** Первые два — одна работа, а не две. Ресайз требует пути обновления геометрии через `ChatView`, `Footer`, `HelpOverlay` и порог ростера; ширина в ячейках требует примитива над графемами и East-Asian-Width. Второму нужен первый, а первому — второй, чтобы не пересчитывать неверно. Это функциональность, а не починка, и делать её внутри флоу, посвящённого дефектам, значит смешать два вида риска.

Третий — изменение протокола: `room.get_transcript` получает `limit` и курсор, а `room.get_state` — последний `seq`, иначе холодный вызов не имеет другого варианта, кроме как забрать весь лог одним куском. Это решение о поверхности инструмента, и ему полагается собственная запись здесь, а не патч внутри исправительного флоу.

**Отвергнутая альтернатива.** Доделать всё в 001. Отклонено: флоу с замороженными критериями приёмки закрывается тем, что эти критерии выполнены. Дописывание в него функциональности размывает и критерии, и смысл слова «выполнено».
