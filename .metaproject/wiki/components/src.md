## Overview

The `src` module provides the core CLI interface and writer coordination for roomyx. It handles command routing through `cli.ts`, enforces single-writer discipline through a lease-based concurrency system in `writer-lease.ts`, and protects critical sections with a lockfile mechanism in `lockfile.ts`. These primitives ensure that only one process can modify a room log at any time, preventing corruption and maintaining consistency in append-only transcripts.

## How it works

The module is organized around three layers: the command-line interface layer (cli.ts) parses flags and routes commands like `room new`, `room append`, and `serve`; the writer coordination layer (writer-lease.ts) implements a heartbeat-based lease system with tokens to track which process holds write access; and the synchronization layer (lockfile.ts) provides low-level mutual exclusion for critical sections that modify files. The lease system solves the inference problem: a one-shot `roomyx room append` command cannot hold a lease (it would expire), so it leaves a tombstone instead. A held lease indicates an attached dispatcher that will keep refreshing. The lockfile uses ownership tokens to prevent a stale holder from deleting a successor's lock.

## Key concepts

**WriterLease** — A JSON file that records who holds write access: it contains a token (UUID), process ID, heartbeat timestamp, and optional tombstone/takeover metadata. A lease is "held" if fresh within LEASE_STALE_MS (30s), "stale" if not refreshed, or "released" if the holder left a tombstone. **LeaseState** — An enumeration of the three possible states when checking a lease (held, absent, stale, or released). **LeaseRenewal** — The outcome of refreshing a heartbeat: refreshed (deadline moved), reacquired (nothing claimed it), or displaced (another writer took it). **LEASE_HEARTBEAT_MS** (5s) and **LEASE_STALE_MS** (30s) set the refresh interval and staleness window. **withLock** — A synchronous mutual-exclusion function that acquires a stale-aware lockfile, runs a critical section, and releases the lock using an ownership token.

## Main flows

**Append with active writer**: `cli.ts` parses `room append --body "..."`, calls `readWriterLease()` to check who holds the log; if held by a live process, refuses. If absent or stale, calls `acquireWriterLease()` to write a new token. Critical section uses `withLock()` from `lockfile.ts` to prevent concurrent registry writes, then appends the message. On exit, `releaseWriterLease()` unlinks only if the token matches. **Server heartbeat**: An attached dispatcher in `server/` calls `renewWriterLease()` every LEASE_HEARTBEAT_MS; if held, updates the timestamp; if stale but unchanged, reacquires with fresh token; if taken over, reports displacement. **Takeover**: `room append --take-over` acquires the lease forcefully, records prior holder metadata in `takenOverFrom`, writes the message under `withLock()`, then calls `tombstoneWriterLease()` to leave a released tombstone before exiting. The next append sees the tombstone and refuses to re-acquire.
