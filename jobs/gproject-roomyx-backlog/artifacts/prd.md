## Executive Summary

`@mrciphersmith/roomyx@0.4.0` is shipped, installable and documented. In fifteen
reproduced places its documentation describes a program that does not exist. This
is not a gap between what the software does and what users want; it is a gap
between what the software does and what its own README, walkthrough and decision
register say it does. Ten of the fifteen are scheduled here. Every one of them is
a broken written promise, and the definition of done is that the promise and the
behaviour agree (`D_success_metric`).

The work has two readers. A human at a terminal cannot create the log the README
tells them to serve, cannot read the transcript they attached a TUI to read, and
is told a healthy server is disconnected. An LLM agent driving the same CLI types
`--help` on an unknown command and starts a server. Several findings are mild
through the first lens and severe through the second; the CLI-grammar work exists
because of the second (`D_audience`).

Exactly one finding has an actor who is not the operator: an unauthenticated
loopback port that a web page can reach, carrying a tool that writes a
caller-supplied path. Its exploitable half ships first, in week one, ahead of the
ranked list — behind a shared HTTP transport that is extracted once so the fix
cannot land in one of two duplicated files. Two entries in
`docs/roomyx/decisions.md` currently mislead the next reader; correcting them is
not a chore appended to the code, it is two blocking stories with a named
approver.

Both orderings are given by the source of truth and **both must survive into
implementation** (`D_ranking_axis`). They are different lists and mean different
things. Every place this document enumerates work, it says which one it is using.

|---|---|---|
| **Build order** (this is the work queue) | ship-now (S1, S2, S3, S4) → **R3** → **R4** → **R8** → **R2** → **R1** | The order an implementer executes in. Reflects dependency, gating and evaluability. |
| **Ranked by weight** (this is *not* a work queue) | **R1**, **R2**, **R8**, **R4**, **R5** | The room's assessment of value. Recorded so the reasoning is legible; it is not a schedule. |

Facts that are deliberate and must not be "corrected":

- **R5 is in the ranking and not in the build order.** Its exploitable half ships
  ahead of everything as S2; what remains (the reaper and the amendment) sits
  after the build order's items.
- **R3 is in the build order and not in the ranking.** It was excluded from the
  ranked five for gating reasons, not value reasons (criterion 3: 10/10).
- **The named failure mode**: an implementer reading the ranked five as a work
  queue starts with a three-day render rewrite for rooms they have no supported
  way to create.

**Prerequisite standing outside both lists**: the HTTP transport extraction
(US-003) precedes **S2** and **R5**. It is not a finding, has no rank, and is not
priced against any item's size.

## Technical Foundation

**Stack** (unchanged, `D_level`): Bun runtime, shipped TypeScript with no build
step, ESM, `strict` + `noUncheckedIndexedAccess`, `bun test` as the only test
runner, `bun run check` as the only gate. Dependencies: `@modelcontextprotocol/sdk`
(floor moving to `>=1.25.0`), `@opentui/core ^0.5.11`, `zod ^4.5.4`. **No
dependency is added by this remediation.**

**Architecture** (recorded, not invented — `architecture.md` §1): layered CLI +
two MCP servers over loopback HTTP, feature-foldered under `src/`. No DI, no
repository pattern, no service layer. The dependency rules in §1.2 hold today and
must keep holding — in particular *the TUI never reaches into a component's
internals*, which is why the scroll API is a method on `ChatView` and not an
exposed `ScrollBoxRenderable`.

**Key MUST constraints** governing this PRD (full list in
`tech-bestpractices.md`; each story names the ones it is bound by):

- **PKG-1/2/3/5** no build step; `bin` targets live under `files`; node-shebang
  launchers that `exec` bun; **never** fetch, install or bootstrap Bun.
- **TR-1/2/3** extract `src/server/http-transport.ts` **before** S2 or R5 changes
  transport behaviour, as its own commit inside S2's PR; afterwards a
  transport-level change lands in **exactly one place** — a requirement reading
  "apply in both files" is a violation.
- **SEC-1** SDK floor `>=1.25.0` inside S2's definition of done.
  **SEC-3** every security acceptance criterion asserts **effect, not
  configuration**. **SEC-4/5** allowlists built from the bound port inside
  `createSession()`; both `allowedHosts` and `allowedOrigins`. **SEC-9** the guard
  is never described as authentication.
- **UI-1/2/3/4/5/6/7** no scroll state machine; the seq-1 fix is
  `horizontalScrollbarOptions: { visible: false }`; keys delegate to
  `ScrollBoxRenderable.handleKeyPress`; `pageup`/`pagedown`/`home`/`end` for the
  transcript with `up`/`down` staying on the roster (**W-007**: `Home`/`End`
  replace R11's `Ctrl-U`/`Ctrl-D` because all four ruled keys are implemented
  natively and half-page scrolling would need its own delta arithmetic — the
  hand-rolled scroll math UI-1 forbids); `wrapMode: "word"`; fixed intra-R1 order.
- **CLI-1/3/4/6** one parser; `--help` to stdout, exit 0, no side effect; loud
  rejection of unknown flags and unparseable values; `serve` → port `0`, `mcp`
  stays `4320` with the README edit in the same commit.
- **TEST-1/3/4/10/12** zero mocking libraries; R1's seq-1 test observed red first;
  S2's test asserts 403 / `-32000` from a real cross-origin request; the
  extraction is validated by the existing seven suites **without editing them**;
  never assert a config value where an effect is observable.
- **DEC-1/2/3** amendments in Russian `## D-NN` / *Решение / Причина / Отвергнутая
  альтернатива* shape; **every reference to a `D-01` names its file** — there are
  two registers and both contain a `D-01`.
- **REL-1/2/3/4** `release.yml` keeps its name; `v*` tag stays the only trigger;
  S4 is exactly `bun install` → `bun install --frozen-lockfile`; README consistent
  at tag time.

#### US-005: Close the cross-origin door, and raise the floor that makes the guard real

**As an** operator with a browser open
**I want** both transports to reject spoofed-`Origin` and rebound-`Host` requests
before dispatch, on the SDK version actually installed
**So that** a web page cannot complete a handshake against my loopback port and
read my private room transcript (G6)

**Acceptance Criteria — all effect-level:**
- [ ] A real cross-origin request carrying `Origin: https://evil.example` against
      a really-running server receives **HTTP 403 with JSON-RPC error code
      `-32000`**, and does **not** complete the `initialize` handshake. Re-running
      the room's 400-POST reproduction yields **0/400 accepted** (was 400/400)
      (SEC-3, TEST-4).
- [ ] A request carrying a rebound `Host` (e.g. `Host: roomyx.attacker.test`)
      against the same server receives **403 / `-32000`** (SEC-3, SEC-5).
- [ ] **roomyx's own client gets 200.** The TUI client and `isRoomLive()` — both
      of which send **no** `Origin` header — complete the handshake against the
      bound ephemeral port. A test asserts this positive case explicitly; it is
      the case a naive fix breaks (SEC-4, `D_sdk_floor_rejected`).
- [ ] **No acceptance criterion asserts a configuration value.** A test that
      checks `enableDnsRebindingProtection === true` in an options object is a
      violation and is rejected (SEC-3, TEST-12).
- [ ] `allowedHosts` is built from the **bound port**, lazily, inside
      `createSession()` — i.e. after `listen()` — as `127.0.0.1:<port>` /
      `localhost:<port>`. A static, port-less allowlist is an outage, not a fix
      (SEC-4, `D_guard_allowlist`).
- [ ] **Both** `allowedHosts` and `allowedOrigins` are configured; they defend
      different attacks and neither alone is sufficient (SEC-5).
- [ ] The header check is **not hand-rolled** in roomyx's handler; it is the SDK
      constructor options on the transport (SEC-11).
- [ ] `package.json` declares `@modelcontextprotocol/sdk` at **`>=1.25.0`**, inside
      this story's definition of done rather than as a follow-up (SEC-1,
      `D_sdk_floor_ruling`). `>=1.13.3` is rejected: pre-1.24.0 rejects
      `Origin`-less requests and would 403 roomyx's own client.
- [ ] The change lands in **exactly one place** — `src/server/http-transport.ts`.
      Any diff touching the guard in two files means US-003 was skipped (TR-3).
- [ ] The **D-06 amendment (US-002) is in this commit** (DEC-3).
- [ ] Neither the code comments, the README, the amendment nor this PRD describe
      the guard as authentication (SEC-9); no token, credential or session secret

## Security Requirements

All derived from `tech-bestpractices.md` §3; none invented here.

1. **Every security acceptance criterion asserts effect, not configuration**
   (SEC-3, TEST-12). The permitted forms are: an HTTP **403** with JSON-RPC code
   **`-32000`**; a **404**; a file present or absent on disk; RSS returning to
   baseline. Asserting `enableDnsRebindingProtection === true` in an options
   object is a violation and is rejected in review.
2. **The positive case is a security criterion too.** roomyx's own `Origin`-less
   client must receive **200**. A guard that 403s the product is not a fix
   (SEC-4, `D_sdk_floor_rejected`).
3. `allowedHosts` is built from the **bound port**, inside `createSession()`,
   after `listen()` (SEC-4). Both `allowedHosts` and `allowedOrigins` are
   configured (SEC-5).
4. The floor is `@modelcontextprotocol/sdk >=1.25.0`, inside S2's definition of
   done (SEC-1).
5. The guard is **not authentication** and is never described as such (SEC-9). No
   token, credential or session secret is introduced (SEC-10).
6. The header check is not hand-rolled (SEC-11).
7. The network tool has no caller-supplied path; the CLI keeps its literal-path
   escape hatch (SEC-6).
8. S4 ships with or before S2 (SEC-2); S1 keeps its own commit and shares S2's PR
   (SEC-7).

## Testing Requirements

- **Zero mocking libraries** (TEST-1, TEST-11). Real `serve()` on `port: 0`, real
  `StreamableHTTPClientTransport`, real `Bun.spawn`. `mockInput` from
  `@opentui/core/testing` is a keyboard driver and is permitted.
- **Red-first where the finding is a missing assertion**: US-012's seq-1 test is
  written against current code and observed failing before the fix (TEST-3).
- **The extraction is validated by the existing seven suites with zero test files
  edited** (TEST-10). Needing to edit one means the extraction changed behaviour.
- Explicit `bun:test` imports, one `describe` → `test` level (TEST-2); temp dirs
  and handle cleanup per TEST-5; poll-until-deadline, no fixed sleeps (TEST-6);
  test names carry the AC in parentheses (TEST-7); render tests via
  `createTestRenderer` (TEST-8).
- **Pyramid shape is descriptive, not a quota**: ≈60% integration / 25%
  subprocess-e2e / 15% pure unit. Add the test whose failure mode matches the
  finding; do not add a unit layer to hit a ratio.

## Open Questions

**These belong to the owner (MrCipherSmith) at Phase 6. This PRD is written to
remain correct under any answer to each, and deliberately resolves none of them
(REL-5, REL-6, `D_deferred_to_owner`).**

- **Q1 — Release packaging shape.** Which version do the ten scheduled items ship
  as; do S1, R8 and R4 bundle into one release or split? A3 is explicitly
  low-confidence and Phase 4 must not assume it. *No story above names a version
  number or a release boundary.*
- **Q2 — Does a `CHANGELOG.md` get created?** S1 is required to have "its own
  changelog line" and no `CHANGELOG.md` exists; the alternative is a dedicated
  commit title that `--generate-notes` surfaces. *US-004 requires a distinct
  commit; US-015 requires the line to exist "wherever the project decides that
  line lives".*
- **Q3 — Is the release smoke test strengthened?** `release.yml`'s
  `roomyx --help > /dev/null 2>&1 || true` discards output and exit code and has
  passed every release while `--help` exits 1. REL-5 says it *should* lose the
  `|| true` once US-010 gives `--help` real semantics and US-009 changes what
  `bin/roomyx` is — and explicitly defers the decision. *US-006 and US-010 both
  state they do not touch it.*
- **Q4 — How do R3 and R8 divide `src/cli/seed.ts`?** R8 unifies three parsers,
  one of which is `seed.ts:17`; R3 may supersede that file entirely. R3 goes first
  by build order and R8's parser scope is settled after it lands. *US-008 and
  US-010 are each written to hold whether `seed.ts` survives, is absorbed, or is
  deleted.*
- **Q5 — R5's reaper shape** (raised by `architecture.md` §8.2, not one of the
  four deferred questions): `terminateSession()` fixes roomyx's own clients but
  not a third-party MCP client that simply disconnects. Whether a time-based idle
  reaper is also required is an R5 scope question. *US-014's criteria are stated
  as effects (RSS to baseline, 404) so they hold under either implementation.*
