# roomyx — Decisions

Version: 0.7.2

Формат по конвенции keryx (`docs/requirements/keryx-mcp-client/decisions.md`): решение + причина + (где применимо) отвергнутая альтернатива. Нумерация локальна для этого пакета.

## D-01: MCP-сервер только читает состояние и принимает команды; лог по-прежнему пишет только диспетчер

**Решение.** `room.post_owner_command` передаёт команду диспетчеру через MCP, но сам сервер никогда не пишет напрямую в append-only лог комнаты.

**Причина.** Вся консистентность startup-room держится на правиле "единственный писатель" (см. находки Омара в мета-ревью фреймворка, `../startup-room-framework/README.md`). Если TUI получит право писать в лог напрямую, comната получит два независимых источника мутаций — ровно тот класс бага (гонка записи), который мета-ревью уже определило как риск. Дешевле держать TUI строго read+propose, никогда write.

## D-02: MCP, не файл-лог, для транспорта TUI↔оркестратор

**Решение.** Выбран MCP-сервер (`prd.md` R2), а не более простой вариант "оркестратор пишет JSON-lines файл, TUI его читает".

**Причина.** Explicit trade-off, обсуждённый с оператором: файл проще (ничего нового не изобретать, лог уже существует), но не даёт естественного места для интерактивных команд (R5) и структурированных per-agent запросов (R4) без надстройки поверх файла, которая по сути реализовала бы половину MCP заново. Оператор выбрал функциональность (модалки + команды) важнее простоты транспорта.

**Отвергнутая альтернатива.** Файл-лог + отдельный, самодельный command-канал (например, второй файл для команд, который диспетчер поллит). Отклонено: два самодельных механизма (чтение состояния + приём команд) добавляют больше сложности, чем один MCP-сервер, и не переиспользуют ничего готового — тогда как MCP-путь напрямую использует паттерн, уже проверенный в keryx (`src/mcp`, `src/tui/mcp-inspector.ts`).

## D-03: Один провайдер на сессию, без смешивания (v1)

**Решение.** Комната наследует ровно тот провайдер/модель, что и её оркестратор. Не поддерживается: Claude-персонаж + внешний DeepSeek/другой-провайдер-персонаж одновременно в одной комнате.

**Причина.** В процессе обсуждения архитектуры (эта переписка, 2026-09-08) рассматривался более сложный вариант — "приглашённые мнения" от внешних провайдеров через `keryx harness run` — и был явно отклонён оператором как избыточная сложность для текущей цели ("давай пока проще"). Зафиксировано здесь, чтобы не переоткрывать тот же вопрос без явного нового запроса.

**Отвергнутая альтернатива.** Смешанные комнаты (Claude-оркестратор + Claude-персонажи + внешний DeepSeek-персонаж через keryx harness). Технически осуществимо (DeepSeek уже настроен как провайдер в keryx, см. переписку), но добавляет: управление историей для stateless `harness run`-вызовов (нет continue/resume, в отличие от `keryx shell`), вопрос утечки данных на сторонний провайдер, и разметку доверия в логе (внешний участник ≠ owner). Отложено, не отменено — может вернуться отдельным пакетом требований, если понадобится.

## D-04: Не обобщать MCP-клиент keryx под "любой оркестратор" в v1

**Решение.** roomyx v1 не трогает и не расширяет `src/mcp-client` в keryx (сегодня заточен только под `codex mcp-server`, решение D-04 в самом `keryx-mcp-client` пакете).

**Причина.** В однопровайдерной модели (D-03) каждый оркестратор поднимает СВОЙ MCP-сервер и не подключается к чужому как клиент — значит roomyx вообще не нуждается в MCP-клиенте keryx для v1. Экономит реальную работу (обобщение узкоспециализированного клиента — нетривиальная задача, см. keryx's D-04 про "generic client is scope creep без второго реального потребителя").

## D-05: Claude как внешний write-capable агент — не решаем, потому что не относится к делу

**Решение.** Ограничение Anthropic (`claude -p`, `--permission-prompt-tool` принудительно отдаёт "deny" на мутирующие действия в неинтерактивном режиме — задокументировано в `keryx-mcp-client/decisions.md` D-01 самого keryx) явно не является блокером для этого пакета и не требует обхода.

**Причина.** roomyx никогда не запускает Claude как внешне управляемого подчинённого агента — Claude-персонажи всегда идут через нативный Agent/SendMessage того же Claude Code инстанса, что ведёт комнату (см. D-03 выше: один провайдер = сам оркестратор). Вендорское ограничение относится к другому сценарию (кто-то ДРУГОЙ спавнит headless Claude и пытается управлять им извне через MCP elicitation) — не заявляем работу над обходом, потому что обходить нечего.

## D-06: Транспорт — Streamable HTTP на loopback, без токена в v1

**Решение.** MCP-сервер и TUI-клиент соединяются через `StreamableHTTPServerTransport`/`StreamableHTTPClientTransport` (`@modelcontextprotocol/sdk`), сервер биндится только к `127.0.0.1` по умолчанию; без токена/авторизации в этой версии.

**Причина.** Изначально предполагался stdio-транспорт (родительский процесс спавнит дочерний), но архитектура сама требует независимых процессов: оркестратор поднимает сервер как часть своей сессии, TUI запускается ОТДЕЛЬНО пользователем в другом терминале (или позже — оркестратором как дочерний процесс, но не гарантированно в одном родительском дереве) — stdio требует общего parent-child pipe, которого здесь нет по дизайну. HTTP loopback — стандартный путь для независимых процессов на одной машине, и прямо соответствует уже существующему в keryx прецеденту `keryx serve` ("loopback-bound HTTP entry... off by default... Bind address. Loopback unless acknowledged"). Отсутствие токена в v1 — осознанное упрощение: угроза ограничена локальной машиной оператора, тем же уровнем доверия, что и у процесса, который сервер запустил; добавление токена/авторизации становится обязательным условием, если/когда roomyx когда-либо перестанет биндиться только на loopback.

**Отвергнутая альтернатива.** stdio-транспорт с TUI-клиентом, спавнящим сервер как свой дочерний процесс (тогда TUI становится "оркестратором" соединения). Отклонено: это меняет модель "оркестратор поднимает сервер" на "TUI поднимает сервер", что противоречит уже согласованному с оператором разделению ролей (комната остаётся полностью во власти оркестратора; TUI — вторичный, необязательный наблюдатель, который можно закрыть/переоткрыть без влияния на саму комнату).

## D-01a: Поправка к D-01 — «единственный писатель» относится к живой комнате, а не к пакету

**Решение.** D-01 ограничивает **сервер**, а не пакет. Инвариант — «один писатель на живую комнату», а не «roomyx никогда не пишет байты». Из этого следует конкретное разделение:

- `roomyx room new <path>` создаёт лог там, где его нет. Диспетчера ещё не существует, число писателей идёт с нуля к одному, гонки нет. Никакого исключения не требуется.
- `roomyx room append <path>` действительно способен нарушить D-01, дописав в лог, который сейчас ведёт диспетчер. Поэтому команда сверяется с реестром и **отказывается**, если этот путь обслуживает живая комната. `--force` перекрывает отказ для того, кто знает, что делает.

**Причина.** До этой поправки единственным способом создать лог комнаты был файл `src/cli/seed.ts`, который отгружается в пакете, но не объявлен в `bin`, не упомянут в README и документирован только в сценарии тестирования — как вызов через абсолютный путь в глобальный `node_modules`. То есть возможность существовала, была недокументированной и всё равно писала в лог. Поправка ничего не добавляет к тому, что пакет уже умеет: она делает это видимым и **ставит охрану там, где охраны не было**.

Формулировка «D-01 ограничивает сервер, а не пакет» — это довод, а не констатация, и поэтому он записан здесь, а не в сообщении коммита. Аргумент, который живёт в переписке, — это слух, а не решение.

**Отвергнутая альтернатива.** Оставить `seed.ts` как есть и не трогать D-01. Отклонено: время до первой комнаты — главное число этого продукта, а инструкция «дотянись до чужого каталога модулей» его не улучшает. И охраны у той записи всё равно не было, то есть отказ от поправки сохранял бы риск, а не устранял его.

## D-06a: Поправка к D-06 — loopback не исключает браузер

**Решение.** Защита от DNS rebinding включена на обоих транспортах: `enableDnsRebindingProtection` вместе с `allowedHosts` и `allowedOrigins`, которые строятся лениво, из фактически занятого порта, внутри создания сессии.

**Причина.** Рассуждение D-06 — «угроза ограничена локальной машиной, тот же уровень доверия, что у процесса, который сервер запустил» — верно для границы между процессами и не выдерживает границы браузера. Страница, которую откроет оператор, не наследует этого доверия и всё равно достучится до 127.0.0.1. Это не новый вид угрозы, а действующее лицо, которое модель угроз D-06 просто не перечислила. Проверено вживую до починки: `initialize` с заголовками `Origin: https://evil.example` и `Host: roomyx.attacker.test` проходил рукопожатие и позволял вызывать инструменты; в связке с тогдашним произвольным путём у `roomyx.skills.sync` это давало запись в файл по выбору атакующего.

Отсутствие токена, о котором D-06 договорился, при этом не пересматривается. Средство здесь — не аутентификация, а три опции, которые SDK уже даёт. Защита останавливает браузер и не останавливает соседний процесс: локальная программа не пошлёт `Origin` вовсе и пройдёт мимо проверки. Это ровно та граница, которую D-06 и провёл, поэтому называть включённую защиту аутентификацией нельзя.

**Две подробности, которые стоили бы дня отладки.** Первая: `allowedHosts` сверяется точным совпадением со всем заголовком `Host`, вместе с портом, — список из голых имён хостов отвечает отказом собственному клиенту roomyx. Вторая: обе проверки нужны одновременно, потому что закрывают разные атаки. Страница на `http://127.0.0.1:<порт>/mcp` шлёт законный `Host`, её останавливает только проверка происхождения; страница после подмены DNS шлёт `Host: attacker.example` и уже одноимённое происхождение, её останавливает только проверка хоста.

**Нижняя граница версии SDK.** Поднята до 1.25.0, и это часть решения, а не гигиена зависимостей. Измерено по тридцати архивам: защита появилась в 1.13.3, но до 1.24.0 она отвергала запросы вовсе без заголовка происхождения — а их шлёт и TUI-клиент, и проверка живости. Проброс опций в тот транспорт, который здесь используется, начинается с 1.25.0. Наивная граница «где защита впервые появилась» заставила бы продукт отвечать отказом самому себе на установках, которые мы не проверяли.

## D-07: Один HTTP-транспорт на оба MCP-сервера

**Решение.** Сессии, привязка к хосту и порту, отказ от не-loopback без явного флага и корректное завершение живут в одном модуле `src/server/http-transport.ts`. И покомнатный сервер (`roomyx serve`), и управляющий (`roomyx mcp`) — тонкие обёртки над ним: каждый задаёт только фабрику `McpServer`, порт по умолчанию и подпись для сообщения об отказе.

**Причина.** Транспорт был написан дважды, и копии успели разойтись: управляющий сервер при остановке не закрывал свои сессии, а покомнатный закрывал. Это не гипотетическое расхождение — оно уже существовало в опубликованном пакете. При двух копиях каждая правка транспортного уровня требует двух одинаковых изменений, и подписанный тарбол — плохое место, чтобы узнать, что второе забыли. Ближайшие работы это подтверждают: включение защиты от DNS rebinding и сборка протухших сессий обе трогают именно транспорт.

Замер перед вынесением: тела двух серверов различались четырьмя содержательными фрагментами (фабрика сервера, подпись в сообщении об отказе, порт по умолчанию, форма опций). Семь тестовых файлов конструируют эти серверы, и **ни один** не импортирует их внутренности — все ходят через `serve()` и `serveManagement()`. Поэтому вынесение, сохраняющее эти две сигнатуры, не потребовало правки ни одного теста. Это проверено, а не предположено.

**Отвергнутая альтернатива.** Оставить две копии и вносить каждую транспортную правку дважды. Отклонено: единственная причина, по которой это работало до сих пор, — что транспорт почти не трогали. Как только его начали трогать, цена дублирования стала реальной, а страховки от пропущенной второй копии в одиночном проекте нет никакой.

## D-08: Контракт лога принадлежит одному модулю, и от него зависят обе стороны

**Решение.** Zod-схемы строки состояния и строки сообщения живут в `src/log/schema.ts`. И читатель (`store.ts`), и писатель (`write.ts`) импортируют их оттуда; ни одна сторона не объявляет свою. `appendMessage` разбирает конверт перед записью, а не после.

**Причина.** Схемы были только на стороне чтения, а у писателя были одни типы TypeScript — которые стираются ровно на границе CLI, где приходит пользовательский ввод: `--kind` приводился к типу через `as never`. Писатель принимал то, что читатель отвергал, по построению. Одна команда `roomyx room append --kind bogus-kind` завершалась успешно, писала строку, и после этого лог не читался **никогда**: он append-only, команды починки нет, а сервер при этом продолжал подниматься и регистрироваться, так что `rooms list` называл комнату живой, а прикреплённый клиент навсегда показывал «отключено» напротив совершенно здорового сервера.

Это не гипотеза: воспроизведено до починки тремя независимыми ревьюерами и оркестратором, и воспроизведено после — три недопустимых вызова отвергаются, в логе остаётся только заголовок.

**Отвергнутая альтернатива.** Проверять только в CLI. Отклонено: `appendMessage` — экспортируемая функция, её вызовет встраивающий диспетчер, и охранник, который можно обойти, не является охранником. Проверка в CLI осталась, но как формулировка сообщения об ошибке, а не как защита: она называет флаг, который человек набрал, а не поле схемы.

## D-09: Ошибка инструмента — не потеря связи, и переподключение одиночное

**Решение.** `callTool` читает `result.isError` и бросает типизированную `ToolError` с текстом сервера. Циклы опроса сообщают о ней и **продолжают опрашивать**: комната достижима. Разрыв транспорта по-прежнему ведёт к `handleDisconnect`, и это разные пути. Переподключение одиночное: счётчик поколений, который каждый цикл захватывает и проверяет, сохранённый дескриптор таймера и закрытие предыдущего клиента.

**Причина.** Ошибка инструмента приходила прозой, на которой спотыкался `JSON.parse`, — неотличимо от обрыва. Оба цикла ловили это независимо, каждый планировал своё переподключение, и каждое стартовало свежую пару циклов, не останавливая работающие: число циклов удваивалось на каждом сбое. Замерено — одна битая строка в логе увела одного клиента в 510 соединений за десять секунд, при живом и отвечающем сервере.

Второй половиной цены был выброшенный текст. Именно он и был диагнозом — «Invalid message line 2 in …», — то есть единственная фраза, которая сказала бы человеку смотреть в лог, а не в сеть. Теперь она попадает в саму ленту, где читается и переживает прокрутку.

**Отвергнутая альтернатива.** Считать любой сбой разрывом и полагаться на переподключение. Отклонено: это и есть исходное поведение, и оно превращает исправимую ошибку данных в неостановимый шторм.

## D-10: Одна дисциплина блокировки — и для реестра, и для самих данных

**Решение.** `withLock` вынесен в `src/lockfile.ts` и используется и реестром комнат, и `appendMessage`. Выделение `seq` и запись строки — одна критическая секция, а не две.

**Причина.** Реестр получил блокировку после трёх раундов ревью — эксклюзивное создание, перехват протухшей по mtime, токен владельца, чтобы медленный держатель не удалил чужую. Комнатный лог, то есть сами данные, не получил ничего. Три параллельных `roomyx room append` выделяли `seq: 1` все три, и все три строки оказывались на диске. `seq` — курсор транскрипта, поэтому клиент, опросивший сервер между двумя столкнувшимися записями, запоминает `sinceSeq = 1` и **никогда** не получает второе сообщение: оно на диске и невидимо в TUI навсегда.

Странность исходного состояния стоит назвать прямо: защищена была бухгалтерия о данных, а не данные.

**Отвергнутая альтернатива.** Написать вторую, более простую блокировку для лога. Отклонено: три раунда закалки существующей — это ровно та работа, которую вторая копия повторила бы с нуля и, скорее всего, не до конца.

## D-11: Сетевая поверхность сообщает, оператор решает

**Решение.** У MCP-инструмента `roomyx.skills.sync` нет ни `yes`, ни `dryRun`. Он сообщает, что синхронизация **сделала бы**. Сам гейт живёт внутри `syncSkill`, считается один раз и по умолчанию закрыт: без явного `yes: true` не пишется ничего.

**Причина.** `yes` — это то, что выключает предохранитель D-02 от затирания. На CLI это нажатие оператора; по сети это булев флаг, который вызывающий ставит себе сам, то есть не предохранитель вовсе. Хуже того, значение по умолчанию считалось на каждой поверхности отдельно, и поверхности разошлись: CLI брал `--dry-run || !yes`, а инструмент передавал оба как `undefined` — поэтому вызов с одним только `target` писал настоящий файл скилла без подтверждения, по неаутентифицированному loopback-порту, в то время как справка самого CLI обещала «без --yes ничего не пишется».

Это то же рассуждение, по которому из этой схемы ранее убрали `targetPath`. Тот проход забрал путь и оставил гейт.

**Отвергнутая альтернатива.** Оставить `yes` и считать loopback достаточной границей. Отклонено: D-06a уже зафиксировала, что loopback не ограничивает браузер, а D-02 существует ровно затем, чтобы появление настоящего файла скилла было осознанным действием, а не побочным эффектом существования механизма.

## D-12: Три пункта отложены — с причинами, а не молчанием

**Решение.** Обработка ресайза терминала, арифметика по ячейкам отображения и `limit` для `room.get_transcript` в исправительный флоу 001 не входят. Все три остаются в отчёте ревью и в разделе Known в CHANGELOG.

**Причина.** Первые два — одна работа, а не две. Ресайз требует пути обновления геометрии через `ChatView`, `Footer`, `HelpOverlay` и порог ростера; ширина в ячейках требует примитива над графемами и East-Asian-Width. Второму нужен первый, а первому — второй, чтобы не пересчитывать неверно. Это функциональность, а не починка, и делать её внутри флоу, посвящённого дефектам, значит смешать два вида риска.

Третий — изменение протокола: `room.get_transcript` получает `limit` и курсор, а `room.get_state` — последний `seq`, иначе холодный вызов не имеет другого варианта, кроме как забрать весь лог одним куском. Это решение о поверхности инструмента, и ему полагается собственная запись здесь, а не патч внутри исправительного флоу.

**Отвергнутая альтернатива.** Доделать всё в 001. Отклонено: флоу с замороженными критериями приёмки закрывается тем, что эти критерии выполнены. Дописывание в него функциональности размывает и критерии, и смысл слова «выполнено».

## D-13: В `0.x` минорная позиция — ломающая, патч несёт всё остальное

**Решение.** Пока проект в `0.x`, минорная позиция двигается **только** при ломающем изменении: удалённый или переименованный экспорт, команда, флаг, параметр MCP-инструмента; изменённое умолчание, меняющее результат у вызывающего, который ничего не просил; поднятый рантайм-порог. Всё прочее — и починки, и обратно совместимые добавления — идёт в патч. Полностью: `docs/roomyx/versioning.md`.

**Причина.** Не вкус, а то, что `^` уже означает для потребителя. Каретка не даёт измениться самой левой ненулевой цифре: для `1.0.0` и выше это патч и минор, для `0.x >= 0.1.0` — **только патч**. То есть зависимость `^0.6.0` автоматически получает `0.6.1`, `0.6.2` и никогда не получает `0.7.0`. npm уже кодирует ровно то обещание, которое мы хотим дать, и оно держится только если ломающее лежит в миноре и больше там ничего нет.

Альтернатива — обращаться с минором как в `1.x`, то есть «фичи» — лишает минор различающей силы: увидев `0.7.0`, потребитель не может отличить новую возможность от удалённого метода, и единственный безопасный ответ — читать changelog на каждый релиз. Это ровно та работа, ради экономии которой номера версий и существуют.

Стоит назвать и то, чего спецификация **не** говорит. Правила 6, 7 и 8 SemVer 2.0.0 все ограничены `x > 0`, поэтому к нам не относится ни одно. Про `0.x` там сказано только правило 4: «anything MAY change at any time». Значит это наша конвенция, а не соблюдение стандарта, и выдавать её за стандарт было бы неверно. Разрешением ломать что угодно в патче мы не пользуемся: пакет опубликован, и `^0.6.0` в чужом `package.json` — обещание независимо от того, обязывает ли нас спецификация.

**Что показал аудит.** Из семи выпущенных версий верны четыре. `0.2.0`, `0.3.0` и `0.4.0` двигали минор за чисто добавляющие изменения — по этому правилу они должны были быть `0.1.1`, `0.2.2` и `0.2.3`. Ошибка во всех трёх одна: релизу, который ощущался значительным, давали значительно выглядящий номер. Значимость — не та ось; ось — что придётся изменить вызывающему. Перетегировать опубликованное не стали: неверный номер хотя бы стабилен.

**Отвергнутая альтернатива.** Перейти в `1.0.0`, чтобы получить три полноценные позиции. Отклонено: `1.0.0` — это обязательство не менять поверхность MCP-инструментов, команды CLI и формат лога без мажорного скачка, а мы не там. Формат лога получил новое поле в текущем релизе, и в бэклоге лежит изменение протокола `room.get_transcript`.

## D-14: История закрытых комнат — это индекс, а не папка с копиями

**Решение.** Когда комната закрывается, в `.roomyx/rooms/history.jsonl` дописывается одна строка: id, **путь к логу**, цель, сколько было участников и сообщений, когда началась и когда закрылась. Сам транскрипт не копируется никуда и остаётся ровно там, куда его положил оператор. Читают этот индекс `roomyx rooms history`, `roomyx-client --archive` и подсказка в сообщении «нет живых комнат». Открывается закрытая комната только на чтение: `roomyx-client --open <путь>`.

**Причина.** Очевидная форма для «сохранять закрытые диалоги» — папка, в которую лог копируется при закрытии. Здесь она неверна по одной конкретной причине: лог комнаты — append-only и единственный источник истины о сказанном (D-01a). Копия делает второй. Как только копия существует, дозапись в оригинал — а её всё ещё разрешает `roomyx room append --force`, и её штатно делает диспетчер, если комнату подняли снова, — оставляет два файла, которые расходятся, и ничто не фиксирует, какой из них текущий. Читатель различить не может, и неверный ответ приходит молча.

Индекс же умеет сказать то, чего копия сказать не в состоянии: **лога больше нет по записанному пути**. Строка списка несёт это отметкой `!` в самом начале — не фразой в конце, потому что и хвост строки, и позиция перед целью съедаются усечением ровно на тех ширинах, где это важнее всего (60 и 40 колонок соответственно; обе замерены). Теневая копия вместо этого показала бы текст, который уже не совпадает с файлом, который читатель считает открытым.

**Две точки записи, а не одна.** Штатное завершение `roomyx serve` пишет запись до снятия с регистрации. Но комната, убитая сигналом без обработчика, не пишет ничего — а перечитать хочется как раз такие. Единственный момент, когда что-либо вообще замечает её конец, — прочистка мёртвых записей в `listLiveRooms`, поэтому вторая запись стоит там. Обе могут сработать на одну комнату; дедупликация идёт при чтении (побеждает поздняя), потому что это дешевле, чем брать лок на пути завершения.

**Повреждённая строка здесь пропускается, а не поднимает ошибку** — в противоположность тому, что делает `loadRoomLog`. Лог комнаты — это транскрипт, и чтение мимо битой строки молча теряет чьи-то слова. Этот файл — индекс, восстановимый с нуля, и одна битая строка не должна прятать пятьдесят целых комнат. Число пропущенных возвращается и печатается, чтобы поверхность говорила о повреждении, а не выдавала частичный список за полный.

**Отвергнутая альтернатива.** Копировать лог в `.roomyx/history/` при закрытии. Отклонено по причине выше: это второй источник истины для файла, единственность которого зафиксирована D-01a. Отвергнута и промежуточная форма — копировать и помечать копию «архивной»: пометка не решает, какой файл читать, она лишь называет проблему.

## D-15: `roomyx init` спрашивает галочками, а не принимает флаг вслепую

**Решение.** `init` в терминале показывает список того, что он может сделать — скилл для каждого рантайма в двух областях (глобально и в проекте), каталог логов, строки в `.gitignore`, регистрация MCP-сервера, — с точным путём каждой записи. Стрелки/`j`/`k` двигают, пробел отмечает, Enter выполняет, `q` отменяет. **До Enter не пишется ничего.** Через пайп и в CI список не показывается вовсе: `init` создаёт `.roomyx/` и молча выходит, а `--yes` применяет отмеченное по умолчанию без вопросов.

**Причина.** D-02 требует, чтобы появление настоящего файла скилла было осознанным действием, и до сих пор роль этого действия играл флаг `--yes`. Но флаг — это обязательство относительно пути, набранного по памяти: оператор говорит «да» тому, чего не видит. Галочка напротив напечатанного пути — то же обязательство, взятое глядя на цель. Это не ослабление D-02, а более честное его исполнение.

Практическое подтверждение получено в тот же день: оператор поставил пакет, выполнил `init` и ждал, что скилл появится у агента. Он не появился и не мог: `init` клал заготовку в `.roomyx/skills/`, которую не сканирует ни один рантайм, а установка была отдельной командой, о существовании которой ниоткуда не следовало. Команда, после которой ничего не работает, — это не безопасность, это незаконченный инсталлятор.

**Гарантия для не-терминала.** Отсутствие tty означает пайп, CI или запуск из другого агента. Промпт, на который некому ответить, — это зависание, а зависший инсталлятор хуже бездействующего. Проверено мутацией: снятие гарда превращает `roomyx init` в пайпе в тест, падающий по таймауту через двадцать секунд.

**Правило для отметок по умолчанию.** Отмечено то, о чём вопроса по существу нет: рантайм, чей каталог есть на машине; проект, где уже есть каталог этого рантайма; каталог логов, на который `config.json` указывает с первого релиза и который никто никогда не создавал. Остальное — пусто. Отметка по умолчанию не должна приводить к файлу там, где оператор удивится его найти; файл в `~/.cursor` на машине без Cursor — ровно такой случай.

**Регистрация MCP идёт через stdio, а не через URL.** Запись в `.mcp.json` содержит `roomyx mcp --stdio`. URL пришлось бы указывать на порт, где что-то уже слушает, поэтому регистрация, написанная в момент `init`, указывала бы в пустоту до тех пор, пока оператор не вспомнит запустить сервер, — сломанная по умолчанию запись в конфиге. Через stdio клиент сам запускает процесс, и порта нет вовсе. Ради этого у `roomyx mcp` появился флаг `--stdio`, и в этом режиме в stdout нельзя печатать ничего: stdout — канал протокола, одна строка приветствия — ошибка разбора на том конце.

**Что сломалось намеренно.** Таблица рантаймов выросла с трёх строк до девяти (Cursor и Grok, плюс проектная область для всех четырёх). Значит `--target all` теперь пишет девять файлов вместо трёх — существующий флаг делает больше, чем делал, без просьбы вызывающего. По D-13 это минорная позиция, а не патч, поэтому релиз `0.7.0`.

**Отвергнутая альтернатива.** Оставить `init` как есть и просто дописать в вывод подсказку «а теперь выполните skills sync». Отклонено: подсказка в конце вывода — это тот же незаконченный инсталлятор с извинением. Отвергнуто и обратное — делать всё молча без вопроса: это ровно то затирание чужих файлов, ради запрета которого существует D-02.

## D-16: Участники не получают MCP-поверхность; MCP остаётся каналом наблюдателя и владельца

**Решение.** Обмен сообщениями внутри комнаты на MCP не переводится. Конкретно:

1. Участники (персоны-сабагенты) не получают ни MCP-инструментов, ни MCP-клиента. Их ввод и вывод идёт нативным `Agent`/`SendMessage` того же инстанса, что ведёт комнату. MCP-поверхность остаётся тем, чем её сделал D-01: три read-тула плюс проброс owner-команд.
2. Диспечеризация — сбор дельты, знание «кому что уже отправлено», запись строки в лог, проверка формата и `kind` — остаётся обязанностью оркестратора. Это не тот расход, который можно передать серверу.
3. Эскалация («сломалось», «пошло не по плану», «нужен владелец») не получает нового транспорта. Push уже существует — это нативное уведомление на `SendMessage`; работа состоит в том, чтобы срочность стала различимой в логе (отдельный `kind`), а не в том, чтобы построить второй канал.
4. Доставка owner-команды обязана работать между процессами, а не только внутри процесса диспетчера. Сегодня единственный путь — `onOwnerCommand`, который привязывает встраивающий диспетчер, поэтому у `roomyx serve` без встраивания инструмент отвечает `accepted: false` (`src/server/index.ts:92-97`), а README пакета держит «live dispatcher integration … remain `spec ready`, explicitly out of scope for both flows so far». Направление, принимаемое здесь: очередь команд и read-тул к ней, живущие в **том же** MCP-сервере, — не вторая шина (см. D-02).

**Причина.**

1. *Единственный писатель.* `appendMessage` выделяет `seq` и пишет строку в одной критической секции (D-10), а лог append-only и не имеет команды починки: модуль `src/log/schema.ts` существует ровно потому, что писатель однажды принял значение, которое читатель отверг, и комната после этого не читалась уже никогда. Write-тул у участника — возврат того же класса бага, а не удобство.
2. *Курсора чтения не существует.* `room.get_agent_detail` возвращает `lastSeenSeq = max(свои seq)` (`src/log/store.ts:98`) — это «когда я говорил», а не «докуда я прочитал». Знание «кому что уже отправлено» не хранится нигде, кроме контекста оркестратора. Поэтому «перевести участников на MCP-чтение» означает сначала завести это состояние и лишь потом менять транспорт.
3. *Сабагент — не слушающий процесс.* Его ход начинается, когда его позвал родитель: `SendMessage` возвращается сразу, а ответ приходит отдельным уведомлением (`src/bundled-skills/startup-room/SKILL.md`, «Turn loop»). MCP — pull: сервер не может разбудить модель. Даже с клиентом на руках дельту приносит родитель, то есть меняется место сборки текста, а не необходимость в ней. Хуже того: самостоятельно читающий участник склонен перечитать больше дельты — ровно тот квадратичный расход, против которого этот паттерн и написан.
4. *Клиента нет.* `src/mcp-client` в keryx говорит по stdio с `codex mcp-server` и HTTP не умеет; `docs/roomyx/testing-story.md` называет это причиной, по которой `keryx shell` не может прицепиться к комнате. D-04 откладывает обобщение клиента. Подключить участника по HTTP сейчас нечем.
5. В нынешней поверхности нет push-канала, и это не упущение: у сервера нет ни subscriptions, ни нотификаций, а TUI поллит сознательно (`src/client/mcp-client.ts:58`).

**Отвергнутые альтернативы.**

- *Write-тул участнику (`room.post_message`).* Отклонено: нарушает D-01/D-01a, забирает у оркестратора валидацию `kind` и делает append-only лог местом, где ошибку нельзя откатить.
- *Участники сами поллят `room.get_transcript`.* Отклонено: не убирает необходимость пробуждения (причина 3), но убирает дельту как экономию и единственное место проверки формата.
- *Настоящий push «сервер → участник».* Отклонено не по цене, а по внешнему ограничению: у сабагента нет входящего канала, кроме родителя. Это ограничение рантайма, а не roomyx; если рантайм его снимет, вопрос переоткрывается отдельным решением.
- *Второй, самодельный command-канал (файл, который диспетчер поллит).* Уже отклонён в D-02; здесь подтверждается, что п.4 — очередь внутри того же сервера, а не вторая шина.

**Границы.** Пункты 1-3 описывают уже действующее поведение (по коду и логам комнат); п.4 — направление, а не реализация: где живёт очередь, является ли чтение разрушающим и как читающий подтверждает приём — отдельные решения, когда появится реализация. Как показывать адресацию в транскрипте — тоже не предмет этой записи: указатель `in_reply_to` в логе есть и используется (в `docs/roomyx/screenshots/review-room.jsonl` его несут 4 сообщения из 9, два из них — на одно и то же).

## D-17: Адресация показывается тем, что читается — именем и цитатой, а не номером seq

**Решение.**

1. Указатель ответа рендерится именем участника, а не номером: `answer -> Inés`, а не `answer re #4`. Номер seq в интерфейсе не показывается; в логе и в контракте `room.get_transcript` он, разумеется, остаётся.
2. Рядом с именем идёт короткая цитата родительского сообщения, обрезанная по ширине панели. Она нужна потому, что ответ в этой комнате почти всегда уходит не на соседнее сообщение: в `docs/roomyx/screenshots/review-room.jsonl` из девяти сообщений четыре несут `in_reply_to`, два из них указывают на одно и то же, а одно — на сообщение пятью позициями выше.
3. Смысл живёт в тексте, а не в цвете. Направление показывают знак и имя; цвет — только усиление. Палитра сейчас три тона, а repainted-состояние не попадает ни в screen reader, ни в `tee` (`tui-review.md`, находка Ken'а). Знак берётся ASCII: `→` и `↩` East-Asian-ambiguous, и неверная оценка ширины сдвигает перенос всей строки (`message-row.ts`).
4. Формат указателя вычисляется **одной** функцией, которой пользуются строка, поиск и экспорт. Сейчас тег собран дважды (`message-row.ts`, `transcript.ts`) и поиском не находится вовсе, хотя комментарий в `matches()` объявляет, что ищется «то, что читатель видит».
5. Указатель не подавляется сворачиванием заголовка. Сейчас тег рисуется внутри заголовка, а заголовок скрывается для подряд идущих сообщений одного автора (`chat-view.ts` — `showHeader: transcript.startsRun(index)`, `message-row.ts` — `if (options.showHeader)`), поэтому у второго подряд сообщения исчезают и `kind`, и указатель ответа, а набор тегов зависит от активного фильтра: `startsRun` считается по `visible()`.

**Причина.** `kind` и `in_reply_to` пишет диспетчер, и исходный дефект этого места был ровно в том, что их не рисовало ничего: структура challenge/answer существовала в логе и отсутствовала в его просмотрщике. Тег `re #4` исправил это формально и не исправил по существу: номер не разрешается ни во что, пока читатель не отыщет сообщение вручную, и на экране он выглядит так же, как `kind`, — двумя серыми словами в одном месте. В комнате, смысл которой в том, кто кому отвечает, «частично исправлено» означает «не исправлено».

**Отвергнутые альтернативы.**

- *Ветки и отступы по дереву ответов.* Отклонено для ленты. Комната по конструкции broadcast: `SKILL.md` прямо говорит, что `@`-адресация — конвенция для ясности, а не фильтр доступа. В реальном логе дерево вырождено (фан-ин на один seq, глубина 1-2), так что отступы отняли бы ширину ради структуры, которой почти нет. Отступы меняют точки переноса и попадают в известный дефект переноса (`test/client/wrap-defect.test.ts`). И лента — единственный общий порядок чтения; ветвление его дробит. Если ветки когда-нибудь понадобятся, это отдельный режим (как фильтр по участнику), а не замена потока.
- *Подсветка `@Имя` в теле как основной механизм.* Отклонено: в реальном логе адресация идёт прозой, а `@` не встречается ни разу, и выводить адресата из прозы — угадывание.
- *Обратная ссылка на родителе (`answered by …`).* Полезно, но требует менять **уже нарисованную** строку: сегодня путь строго инкрементальный (`appendEntry` → `addRow`), и это было бы первым местом, где старая строка меняется, рядом с `destroyRecursively` и конечным пулом рендереров. Отложено, не отменено.
- *Прыжок к родителю по клавише.* Требует курсора в транскрипте, которого нет: выделение живёт в ростере, а «selection has to mean something visible» остаётся в `tui-review.md` пунктом ниже линии. Отложено до решения о курсоре.

**Границы.** Это решение про показ. Оно не меняет ни лог, ни MCP-поверхность: данных достаточно уже (`in_reply_to` и `kind` есть в конверте, имена — в ростере). Пункты 4-5 — не украшение, а дефекты: указатель, видимый на экране и не находимый поиском, и указатель, пропадающий вместе с заголовком, уже сейчас делают адресацию невидимой. Как обрезать цитату и сколько ей отдавать ширины — деталь реализации, а не решение.

## D-18: Владение писательством — явное; очередь owner-команд живёт в сервере

**Решение.** Дизайн не меняется: в лог по-прежнему пишет диспетчер, сервер в лог не пишет. Меняется то, чем удерживается инвариант «один писатель на живую комнату», и расширяется read-поверхность MCP.

1. **`dispatcherAttached` в `room.get_state`.** Сервер уже знает ответ (`options.onOwnerCommand !== undefined`) и не сообщает его. Снаружи «живая комната» и «живая комната, в которую кто-то диспатчит» сегодня неразличимы — из этого растёт двусмысленность отказа `append` («if it has a dispatcher»), которую сама команда признаёт в своём комментарии.
2. **`--force` заменяется на `--take-over`.** Отказ остаётся у `append`, но переопределение перестаёт быть флагом «всё равно». `--take-over` берёт владение только у мёртвой комнаты или у писателя, чей лиз просрочен.
3. **Лиз владения — машинно-локальный sidecar, а не запись в логе.** Право писать держит тот, кто пишет: CLI или встраивающий диспетчер. Лиз не в логе (лог описывает сказанное, а не то, кто держит перо) и не в реестре (реестр отвечает на вопрос, что отвечает по MCP). Протухание — по образцу `withLock`: у лиза есть срок, после которого его можно забрать.
4. **Запись становится структурной.** `room append --json <envelope>` (конверт целиком, а не набор флагов), `--body-file -` для тел со stdin, `--many` — JSONL со stdin, N реплик за один вызов с непрерывными `seq`.
5. **`room.get_delta_for(agent_id, since_seq?)`** — сервер сам считает дельту участника: всё позже его последней собственной реплики, кроме его собственных. Дефолт назван конвенцией, а не источником правды: истинный курсор — «что я тебе реально отправил», и его знает только диспетчер, поэтому `since_seq` переопределяет дефолт.
6. **Очередь owner-команд живёт в сервере и читается.** Команда, пришедшая по `room.post_owner_command`, остаётся в очереди сервера и отдаётся наружу: read-тул `room.get_pending_owner_commands` и ресурс `room://owner-queue` (с `resources/subscribe` там, где хост это умеет). `onOwnerCommand` остаётся для встраивающих хостов: две дороги, одна очередь. Добавляется `room.ack_owner_command` — подтверждение приёма. Сервер по-прежнему ничего не пишет в лог: строку кладёт диспетчер, прочитав очередь.
7. **Деградация видна в логе.** Запись, выполненная при мёртвой или неотвечающей комнате, добавляет в транскрипт строку `kind: "status"` о смене владельца. Нового типа записи не требуется: `status` уже в `MESSAGE_KINDS`, а правило «state changes must also enter the transcript as ordinary text» уже принято в TUI-ревью.
8. **Обновление состояния (`goal_edit`, `add_participant`) получает представление отдельным решением.** Сегодня его нет: `loadRoomLog` принимает `state` только первой строкой и обязан разобрать каждую следующую как `message`, обновлять state нечем, а `updated_in_round` и `updated_by` в схеме не пишет никто. Пункт перечислен здесь, чтобы пробел не потерялся, но закрывать его этой записью нельзя: он трогает формат лога.

**Форма отказа после этой записи.** Комната мертва — пишем. Комната жива, `dispatcherAttached: false` — пишем без флага: писателя нет, гонки нет (сегодня этот случай требует `--force` и неотличим от гонки). Комната жива, `dispatcherAttached: true` — отказываем; при свежем чужом лизе отказывает и `--take-over`; при просроченном лизе `--take-over` берёт владение и оставляет в логе след из п. 7.

**Причина.**

- **D-01 защищает букву там, где нужен он сам.** D-01 говорит «сервер не пишет» и обосновывает это единственным писателем, но у гонки нет мнения о том, какой процесс пишет: важно, что один. Доказательство, что сегодня инвариант держится не программой: единственный механизм, который его охраняет, — отказ `append`, а бандлед-скилл предписывает целевому пользователю писать через обход этого отказа (`roomyx room append … --force`, `SKILL.md:139`, «**`--force` is required here, and it is correct here.**»). Отказ, который в штатном пути велено переопределять, — не отказ.
- **Перенос записи в сервер даёт принуждение, но ценой доступности:** сегодня падение `serve` комнату не останавливает, а после переноса у модели не остаётся способа записать ни одной реплики. Поэтому выбран другой путь — инвариант удерживается владением, доступность сохраняется.
- **`dispatcherAttached` — не украшение, а то, что делает случай «живая комната без диспетчера» законным без флага.** Сегодня он требует `--force`, то есть того же движения, что и настоящая гонка, — и именно поэтому флаг не может ничего запрещать.
- **Очередь команд — недоиспользованный примитив, а не новый механизм.** D-02 выбрал MCP ради «естественного места для команд» и отверг второй, самодельный command-канал (файл, который диспетчер поллит); очередь **внутри того же сервера** — это выбранное, а не отвергнутое. И это единственная часть комнаты, которую сервер может пушить: команду он получает сам, по HTTP. Транскрипт он пушить не может — файл пишет другой процесс, и сервер узнаёт об изменении, только перечитав его.
- **`get_delta_for` убирает из контекста бухгалтерию, а не суждение:** карту курсоров, ручной фильтр и арифметику `since_seq`. Конвенция не выдумана — `get_agent_detail` уже считает `lastSeenSeq` как максимум своих `seq`.
- **`--json`/`--body-file`/`--many` убирают класс ошибок, а не неудобство:** тело с кавычками и переводами строк сегодня попадает в JSON, который собирает `appendMessage`, а обнаруживается это контрактом чтения — тем самым, который такую строку и отвергнет.

**Отвергнутые альтернативы.**

- *Перенос записи в сервер* как средство принуждения. Отклонено по цене в доступности, названной явно. Не отменено: если когда-нибудь понадобится абсолютное принуждение (у модели не должно быть возможности писать вообще), это единственный способ его дать, и тогда возвращаются стоимость в токенах, токен доступа и вопрос о том, что считать аварийным путём.
- *Оставить `--force`.* Отклонено: он делает отказ необязательным ровно там, где отказ и есть весь механизм.
- *Лиз в логе.* Отклонено: лог append-only и описывает сказанное; запись «кто держал перо» превратила бы его в журнал событий процесса и навсегда осталась бы в истории комнаты шумом.
- *Лиз в реестре.* Отклонено: реестр отвечает на вопрос «что отвечает по MCP», и его чистит `rooms list`; смешение двух вопросов в одном файле уже один раз привело к тому, что комната выглядела живой, не отвечая (см. `log_path` в `types.ts`).
- *`elicitation/create` как канал owner-команд.* Отклонено как замена, принято как дополнение: на elicitation отвечает человек, и в headless-рантаймах он ограничен (территория D-05), тогда как очередь переживает перезапуск TUI и не требует, чтобы у владельца был открыт клиент в эту секунду.
- *Push транскрипта через `resources/subscribe`.* Отклонено: сервер не знает об изменении файла. Путь к нему — либо запись внутри сервера (см. выше), либо fs-watch, который D-02 уже отверг.
- *Курсор чтения в логе как источник правды.* Отклонено: лог описывает сказанное, а не прочитанное, и участники читают не лог, а то, что прислал диспетчер, — множества не совпадают.

**Границы.**

- Это **не абсолютное** принуждение. Лиз различает случаи, а не защищается от процесса, который решил обойти: у процесса есть файловая система, и он может удалить sidecar. Покупается невозможность обойти **по неосторожности** — то есть в штатном пути, где сегодня стоит `--force`.
- Сабагента по-прежнему нельзя разбудить (D-16 п.3). Ветки и указатель ответа (D-17), дефект переноса, один провайдер (D-03) не затронуты.
- Пункт 8 — не сделанное, а названное: представления в формате нет, и решать это этой записью нельзя.
- **Формат лога не меняется:** п. 7 использует существующий `kind: "status"`. Меняются формат `room.get_state` и поверхность тулов, и удаляется флаг → по D-13 это **minor** (0.8.0); в бэклоге уже лежит изменение протокола `room.get_transcript` — тот же релиз.
- `dispatcherAttached` обязан появиться, но обязано ли поле быть required — отдельный выбор по D-13: в `RoomState` уже есть прецедент (`log_path` оставлен необязательным ровно для того, чтобы конструирующие `RoomState` не ломались).

## D-19: Библиотека персонажей едет в пакет, а не остаётся контентом проекта

**Решение.** Пятьдесят интервью-персонажей, наборы `founders/`, `tech/`, `panel/` и опросник `questionnaire-50.md` лежат в `src/bundled-personas/` и публикуются вместе с пакетом. Ставятся командой `roomyx personas` в `.roomyx/personas/`, и это же предлагается галочкой в `roomyx init`. Существующие файлы не перезаписываются никогда; `--force` отодвигает каталог целиком в `.bak-<время>`, а не сливается с ним.

**Причина.** Скилл ссылался на `arena/roles/**/*.md` — путь проекта, из которого roomyx был извлечён. Вне того проекта этого пути нет. То есть скилл, установленный глобально или в любой другой репозиторий, отправлял агента за персонажами по несуществующему адресу, а без персонажей комнату не из чего собирать. Переезжал инструмент, персонажи были контентом arena, но ссылка на них уехала вместе с инструментом и повисла.

Альтернатива — оставить персонажей контентом проекта и просто убрать ссылку — честнее по границам, но оставляет продукт нерабочим из коробки: «поставьте пакет, выполните init, потом принесите откуда-нибудь восемьдесят семь файлов профилей». Рубрика на 50 критериев уже едет внутри скилла ровно по этой логике; персонажи — вторая половина того же комплекта.

**Что это стоит.** Пакет заметно вырастает, и русскоязычный контент попадает в публичный реестр навсегда: из npm не удаляют. Решение принимал владелец контента, не я. Проверено перед публикацией и закреплено тестом: в библиотеке нет ни адресов, ни телефонов, ни ключей — это вымышленные биографии.

**Почему существующие файлы не трогаем.** Персонажи отгружены как markdown именно затем, чтобы их правили. Установка, молча откатывающая правку, — то же самое затирание, ради запрета которого существует D-02. Поэтому по умолчанию файл, который уже есть, пропускается и считается в отчёте.
