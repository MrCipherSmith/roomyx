## Overview

The `src/client` module is the TUI (terminal user interface) client for viewing and interacting with a roomyx server. It exports `runClient`, which establishes a connection to a roomyx server over HTTP, polls for state and transcript updates, renders the transcript and roster on screen with keymap-driven navigation, and handles owner commands when appropriate. The client supports three modes: attaching to a live room, reopening a closed room from disk, or picking from the history of closed rooms.

## How it works

The module has four layers: **index.ts** handles initialization, connection resolution, flag parsing, and mode dispatch (live/archive/history); **mcp-client.ts** maintains the connection to the roomyx server, polls for state and transcript updates with exponential backoff, and manages session lifecycles; **viewer.ts** renders the UI using `@opentui/core`, manages display state like scroll position and selection, and calls keymap handlers; **keymap.ts** maps key presses to actions (scroll, navigate, post message). Support files include `clip.ts` for clipboard operations, `init-screen.ts` for the entry screen, and `owner-prompt.ts` for handling owner commands. Connection resolution (finding or listing rooms by ID) is delegated to `src/installer`.

## Key concepts

**RoomClient** — An HTTP polling client that manages the connection to the server, tracks state and transcript, and fires events on changes. **ConnectionStatus** — One of connecting, connected, or disconnected; distinct from tool errors. **Viewer** — The screen renderer and input handler; manages scroll position, selection, and redraws on updates. **OwnerPromptState** — The state of the owner command modal (idle, opened, or step-specific). **sinceSeq** — The transcript seq the client last saw; avoids re-delivering messages on reconnect. **Keymap** — A mapping from key sequences (e.g., "j" for down, "G" for jump-to-end) to action handlers.

## Main flows

**Connect and poll**: `runClient` calls `resolveConnectionUrl` to find the server, creates `RoomClient` with polling intervals, and attaches event handlers to the viewer; on each state update, viewer redraws the roster and goal; on transcript update, viewer appends or highlights new messages. **Attach to live room**: User provides room ID or URL, client polls `room.get_state` every N seconds and `room.get_transcript` every M seconds, accumulating new messages until the viewer is closed. **Reopen closed room**: User passes `--open <path>`, client loads the log from disk with `loadRoomLog`, and viewer displays it without polling. **Owner command**: When attached and a dispatcher is present, user can press a key to open a prompt; viewer sends the command via `room.post_owner_command`, polls updates, and displays the result.
