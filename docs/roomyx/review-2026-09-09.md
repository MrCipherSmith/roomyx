# Full-repository review — 2026-09-09

Nine reviewers, path mode over 62 files (`src` and `test`), run through
`review-orchestrator`. This is a first-pass report: findings only, nothing
fixed.

## How the run was bounded

Scope came from `keryx review scope --path`, not from a hand-picked list: 62
files seen, 62 retained, nothing dropped.

Reviewer selection came from `keryx review reviewers` (17 bundled, 0
project-local) filtered by `keryx review stack`, which reads `package.json` and
excluded three as incompatible with this stack — `review-backend` (no
nestjs/prisma), `review-frontend` and `review-frontend-conventions` (no
react/mobx). That filter matters: the routing table selects by file shape, and a
`.ts` file looks identical whether or not the repository has React in it, so
without it a React/MobX conventions reviewer would have been dispatched at a Bun
CLI.

Three more were skipped with a recorded reason: `review-core-boundaries` (no
`src/core` or `shared`), `review-flow-graph` (no graph UI), `review-regression`
(scope B is a blast radius from a diff; there is no diff in a path-mode review of
the whole repository).

Model: `keryx review tier` returned `standard` / `session-fallback`, so every
dispatch ran on the session model.

## Verification

**Twelve findings were reproduced by execution in this repository, by the
orchestrator, independently of the reviewer that filed them.** Those are marked
**[reproduced]** below. The rest carry the reviewer's own evidence, which in most
cases includes an executed measurement, but were not re-run here — they are
marked **[reviewer-evidenced]**.

No `review-verifier` wave was dispatched. Direct reproduction is a stronger
check than a verifier agent reading a finding, and it was available for
everything that mattered; the trade is that the reviewer-evidenced findings have
had one pass of scrutiny rather than two, and that is why they are labelled.

## Blockers

### B1 — `roomyx room append` writes what the reader refuses, permanently **[reproduced]**

*Filed independently by `review-architecture`, `review-clean-code` and
`review-logic`.*

The read side validates with zod (`src/log/store.ts`); the write side has no
schema at all, only TypeScript types that are erased at the CLI boundary —
`src/cli.ts:134` casts `--kind` with `as never`, and `--in-reply-to` passes any
finite number.

```
$ roomyx room append r.jsonl --from a --body hello --kind bogus-kind
Appended seq 1 from a.
$ # loadRoomLog(r.jsonl) → Invalid "message" line 2 … expected one of "pitch"|…
```

The log is append-only and roomyx ships no repair command, so the session is
unreadable through every roomyx surface from that moment. `serve` still binds and
still registers, `rooms list` still reports the room live, and the attached TUI
shows `DISCONNECTED — retrying` forever against a healthy server. Same with
`--in-reply-to 0` and `1.5`.

**Fix:** one schema for both directions — `safeParse` the envelope inside
`appendMessage`, and drop the `as never`.

### B2 — an idle attached client kills itself in about 2.7 hours **[reproduced]**

*`review-performance`.*

`remove()` in `@opentui/core` unlinks but does not free; only `destroy()` releases
the native yoga node and TextBuffer. Nothing in `src/` calls `destroy()` except
`renderer.destroy()` at shutdown. `RosterSidebar.setRoster` tears down and
rebuilds every row unconditionally, and `onStateUpdate` calls it on **every**
`room.get_state` poll — every 3 seconds, whether or not the roster changed.

Measured here: **5 leaked renderables per poll** with a 5-person roster that never
changes. The native pool is finite, so this is a ceiling rather than a slow leak.
The reviewer ran it to exhaustion: crash at poll #3275 with
`Failed to create native renderable`, then an unhandled rejection that leaves the
terminal in the alternate screen with mouse tracking on.

**Fix:** `destroyRecursively()` after `remove`, and return early when the incoming
roster is deep-equal to the current one.

### B3 — one malformed log line turns one client into a request storm **[reproduced in part]**

*`review-logic`, `review-performance` and `review-highload`, independently.*

`callTool` does `JSON.parse(content[0].text)` without checking `result.isError`,
so a **tool-level** error is indistinguishable from a transport loss. Both poll
loops catch it and both call `handleDisconnect`, which schedules its own
`connect()`; `connect()` starts a fresh pair of poll loops without stopping the
old ones and without closing the previous client. Loop count doubles per outage.

Reviewer measurements, consistent across two of them: 1 connection → 510 in ten
seconds; RSS 131 → 374 MB in forty seconds and still climbing; the server
minted 261 sessions in ten seconds from one client. Reproduced here: `serve` with
a client attached does not exit on SIGTERM (see M1), and the underlying
`isError`-blindness is visible in the source.

The trigger is ordinary — B1 produces exactly the malformed line this needs.

**Fix:** check `result.isError` and surface tool errors as a system line without
disconnecting; make reconnect single-flight with a generation counter; back off.

## Major

### M1 — `serve` never exits on SIGTERM while a client is attached **[reproduced]**

*`review-logic`, `review-highload`.*

`httpServer.close()`'s callback waits for every connection to end, and
`closeSessions` — the thing that would end them — is *inside* that callback.

Measured with a control: with a client attached, still running 12 s after
SIGTERM; with no client attached, exits cleanly. `roomyx mcp` shares the code.

Two consequences beyond the hang. `src/cli.ts` deregisters **before** closing, so
the room disappears from the registry while the process keeps the port — the
room is invisible to `rooms list` and to the client, `room append` silently loses
its D-01a guard for that log, and the next `serve` on 4319 fails with EADDRINUSE.
And the SIGKILL needed to end the hang is what leaves the stale entry that M4
then resurrects.

*This is also the bug the orchestrator misdiagnosed earlier the same day, when a
capture script "hung on `wait`" and the hang was attributed to shell job
control.*

### M2 — concurrent `room append` produces duplicate `seq` **[reproduced]**

*`review-highload`.*

`nextSeq` reads the whole file and returns `max+1`; `appendFileSync` then writes.
Nothing between them. Three concurrent appends here:

```
writer 2 got seq 1
writer 1 got seq 1
writer 3 got seq 2
seqs on disk: [1, 1, 2]
```

`seq` is the transcript cursor, so a client polling between the two colliding
writes records `sinceSeq = 1` and never receives the second message — on disk,
invisible in the TUI, permanently. The registry got a lockfile for exactly this
shape; the data did not.

### M3 — a roster id walks the transcript export out of the working directory **[reproduced]**

*`review-security-code`.*

`filtered.id` is interpolated into the export filename and handed to `join`, which
normalises `..`. `parseRoster` and `rosterEntrySchema` constrain neither half.

```
roster id "../../../../../tmp/pwned"  →  writes /tmp/pwned.txt
status bar says:  written to ./roomyx-transcript-…
```

Whoever authors the room log — the `--roster` argument, the dispatcher, or an
agent that can write the log — chooses where the operator's `w` keypress writes,
and the operator is told the opposite of what happened. Bounded by `wx` (never
overwrites) and the forced `.txt`.

### M4 — `isRoomLive` proves something answers the port, not that it is that room **[reviewer-evidenced]**

*`review-logic`, `review-highload`.*

`pid` and `logPath` are stored in the registry and never consulted. Every `serve`
defaults to port 4319, so a room that died without deregistering is resurrected as
live by the next room that binds the port. The reviewer reproduced both
directions: `roomyx-client --room <dead-id>` silently renders a different room's
transcript under the dead room's id, and `room append` refuses a log nothing is
serving.

### M5 — the MCP skill-sync surface writes without the gate the CLI has **[reproduced]**

*`review-security-code`, `review-logic`.*

`yes` is exposed on the tool's input schema and passed to `syncSkill`, and the
defaults are inverted relative to the CLI: `src/cli.ts:268` computes
`dryRun = flags["dry-run"] === true || !yes`, while the tool passes both through
as `undefined`. The CLI's help says "Without `--yes` nothing is written"; on the
network surface that is not true.

This is the same class as the `targetPath` parameter removed from this tool
earlier the same day. That removal took the path and left the gate.

### M6 — MCP sessions are never released **[reviewer-evidenced, three reviewers]**

*`review-security-code`, `review-performance`, `review-highload`.*

`sessions` loses an entry only via `onsessionclosed`, which the SDK fires only on
an HTTP DELETE. Nothing in roomyx sends one: `client.close()` aborts the local
controller, and `terminateSession()` — the method that sends the DELETE — appears
nowhere in `src/`. No TTL, no cap, no reaper.

Measured by two reviewers independently: ~70–78 KB retained per abandoned
session, linear across 600 cycles. Every `rooms list`, every `room append`, every
client start and every reconnect adds one. An abandoned session id also stays a
fully routable handle to the room for the life of the process — three clients
closed, then a raw POST replaying each recorded session id returned HTTP 200 with
a full `tools/list`.

### M7 — nothing responds to a terminal resize **[reviewer-evidenced]**

*`review-layout`.*

Every dimension is read once at construction. There is no resize listener in the
repository, and `Footer.setWidth` has no caller.

Measured 100x24 → 60x16: the footer row disappears from the frame entirely,
`pageSize()` still returns 22 so PgUp overshoots by 9 every press, and
`isRosterVisible()` still returns true at width 60 — the roster keeps 24 of 60
columns, the exact geometry the breakpoint exists to prevent, while the footer
also suppresses the participant count that compensates for a hidden roster.
Enlarging to 140x40 leaves a 100x24 island. None of it recovers without a restart.

### M8 — the help overlay overflows on any terminal shorter than 20 rows **[reproduced]**

*`review-layout`.*

`height: Math.min(rows().length + 5, options.height - 2)`. The clamp is what makes
it short.

```
H=20  └────────────────────────────────────────────┘
H=19  └─?─or─Esc─closes────────────────────────────┘
H=17  └─q────────────quit──────────────────────────┘
```

At H=19 this is precisely the defect the comment above that line says was fixed —
reintroduced by the clamp added in the same edit. Below H=17 the close hint is
gone entirely while the overlay still swallows the keyboard, and M7 means the user
cannot resize out of it. 17–19 rows is an ordinary tmux split.

### M9 — the footer measures code units and calls them columns **[reviewer-evidenced]**

*`review-layout`.*

`left.length`, `gap`, and the budget handed to `footerHints` are all
`String.length`. The left half carries `filter: ${name}` and `/${query}` — room
and user text.

Measured at width 100: an ASCII name renders all five hints; a CJK participant
name (45 code units, 55 cells) cuts `command` and `q quit` off the row; a longer
one leaves `↑/↓ scroll ·` — a dangling separator and one surviving hint. So a
CJK-named participant deletes the only on-screen statement of how to quit. Seven
combining marks push the block seven columns clear the other way.

### M10 — a long participant name renders an empty roster row **[reproduced]**

*`review-layout`.*

`TextRenderable` with `height: 1` and default word wrapping in a fixed 24-column
box: a name that does not fit wraps to a second line that `height: 1` then clips,
so the whole trailing word disappears rather than being truncated at the edge.

```
name length 22 → "> NNNNNNNNNNNNNNNNNNNNNN"
name length 23 → ">                       "
```

`j`/`k` still move onto that row and Enter still filters by it, so the filter is
attributed to a participant whose name is nowhere on screen. CJK cuts mid-name at
exactly 24 cells, abutting the stream with no separating column. The same shape is
in `StatusBar`, which also carries the export-failure notice.

### M11 — `room.get_transcript` has no `limit` and its consumer is a model **[reviewer-evidenced]**

*`review-performance`.*

`since_seq` is the whole input surface, and nothing else exposes the room's last
seq, so a cold caller has exactly one option: `since_seq: 0`, the entire log in one
`content[0].text`. At this repository's own message density that is 1.57 MB at
1000 messages — on the order of 400K tokens. A room long enough to be worth
reading back is a room no agent can read back.

### M12 — the regression tests do not hold the fixes they were written for **[reproduced]**

*`review-testing-practices`, by mutation.*

Each fix deleted or inverted one at a time, then its own named test file run:

| mutation | its test file |
| --- | --- |
| delete `horizontalScrollbarOptions: { visible: false }` | **6 pass, 0 fail** |
| put `renderer.destroy()` before `roomClient.stop()` | **3 pass, 0 fail** |
| delete the three `if (this.stopped) return;` guards | **3 pass, 0 fail** |
| delete the signal-handler loop | 1 pass, 2 fail ✅ |

Only the last is actually pinned. The first was a genuine barrier when it was
written and stopped being one when the test was rewritten for the new typography
layout — alternating speakers and taller rows left slack in every case, so no
height reaches the state where one stolen viewport row matters. Nobody re-ran the
mutation after the rewrite.

Against the full suite: swapping `postOwnerCommand`'s arguments and corrupting its
tool name — 201 pass. Changing `exportTranscript` from `wx` to `w`, so it silently
overwrites, and dropping the collision suffix — 201 pass.

### M13 — the timing margin in the render tests is under 2x **[reviewer-evidenced]**

*`review-testing-practices`.*

`settle(renderOnce, ms = 200)` stands in for a condition wait, in a file that
imports `waitFor` and then neuters it as `waitFor(() => true)`. Measured: 150 ms
passes, 100 ms fails one test, 60 ms fails two. A 2-vCPU CI runner is an ordinary
2x slowdown. The two shutdown tests likewise assert only negatives after a fixed
2 s, so a client that never connected satisfies all three assertions.

## Minor and info, in brief

- **`ManagementServeOptions` is declared twice, byte-identical** (`src/mcp-management/server.ts:24` and `:92`). Filed by three reviewers. TypeScript merges rather than rejects, so removing a property from one copy does nothing. **[reproduced]**
- **Dead surface after the modal removal:** `RoomClient.getAgentDetail` (comment still describes the deleted modal), `getLastSeenSeq`, `Footer.setWidth`. `jumpTo`'s `direction` parameter is discarded with `void direction;` while three call sites pass a real-looking literal; `commandHelp`'s `name` is unused. **[reproduced]**
- **The search counter prints `0/N`** — `applyFilter` resets `matchCursor` to −1 without clearing the query, so the footer renders match zero of two. **[reproduced]**
- **`--toString x` is accepted silently** — `specs[name]` resolves through the prototype chain, defeating the unknown-flag check for five names. No pollution is reachable; filed `info` because no cost to a user can be named. **[reproduced]**
- **`JSON.parse` sits outside the guarded path** in five places, so a log line that is not valid JSON throws a bare `SyntaxError` instead of the file-and-line message the surrounding code was written to produce.
- **`roomyx init` clobbers the staged skill copy** with no hash check, backup or gate — the operation `syncSkill` refuses — while the two neighbouring writes are guarded and the function's comment promises "never-clobbering".
- **The roster breakpoint is non-monotonic:** 79 → 80 columns costs the transcript 22 columns and adds a wrapped row to every message, and it does not recover until 106. 80 is the most likely width a user lands on.
- **`Transcript.matches()` rescans on every call** — five times per `n` keypress and once a second from the footer timer — with nothing cached against the three tracked inputs. No cost at any room size that exists; 40 ms per keypress at 3000 entries would exceed the 30 fps frame budget.
- **`loadRoomLog` re-reads and re-validates the whole file per tool call.** Measured 0.26 ms at 16 messages, 15 ms at 3000. Not a bottleneck at real sizes; recorded because M11 is the same read and is a cost today.
- **Layering:** `src/client/owner-prompt.ts` imports the protocol vocabulary from `src/server/index.ts`, and `src/client/index.ts` imports connection resolution from `src/installer/`. Both run sideways or upward; the first pulls the MCP SDK and zod into a module documented as a pure state machine.
- **Two `PromptKey` interfaces and two printable-key tests** in the two prompt state machines; **two copies of the message tag formatter** in `message-row.ts` and `Transcript.toText`, which is the pair that keeps the export matching the screen.
- **`withLock`'s 23-line rationale sits above the wrong function**, so the lock protocol's reasoning is invisible at the function implementing it.
- **`test/log/store.test.ts` leaks two temp directories per run**, alone among the files that make them; 136 had accumulated on this machine.
- **The `test.failing` tripwire is sound** — verified that Bun fails the run when such a test passes, and that the companion ordinary test at width 120 is what stops a broken harness from keeping it green. One narrowing: it is binary across three widths, so a partial upstream fix stays invisible.
- **Three abstractions judged load-bearing, not ceremonial:** `http-transport.ts` (both servers, and it carries the session map, the lazily-built rebinding allowlists and `closeSessions`), `keymap.ts` (dispatcher, footer and help all generated from one table), `transcript.ts` (the model filter, search, run-collapsing and export all stand on).

## What this review did not cover

`docs/**` and `.metaproject/**` were out of scope. Ambiguous-width rendering
(`↑/↓` and `·` are East-Asian-ambiguous, and `message-row.ts` states a rule
against exactly that class) could not be measured: the headless renderer has one
fixed width policy and exposes no ambiguous-width setting. It is filed as `info`,
unverified, rather than as a runtime claim.
