## Overview

The `scripts` module provides three non-unit test harnesses for stress testing, fuzzing, and replaying: soak (simulates a long-running client with compressed time), fuzz-log (generates malformed logs to test error handling), and replay (reconstructs a room session from a log for debugging). These scripts catch volume-dependent defects invisible to unit tests.

## How it works

**soak.ts** runs a client continuously, polling a server at compressed intervals (20ms instead of 3s) to simulate hours of operation in minutes; it tracks memory, renderable pool size, and connection counts to detect resource leaks. **fuzz-log.ts** generates 2000+ random message variations, including schema violations, and feeds them to loadRoomLog to verify error messages and crash handling. **replay.ts** reads a room log, simulates the client's view by rendering each message, allowing breakpoint debugging of client rendering logic. All three use temporary logs cleaned up after execution.

## Key concepts

**Soak test** — Stress test under compressed time to find long-running leaks. **Fuzzing** — Random input generation to expose edge cases. **Deterministic replay** — Reconstructing a session state to debug specific issues. **Trend assertion** — Checking that a metric is stable over time, not guessing thresholds.

## Main flows

**Soak test**: Start server, attach client, loop: make state change, poll 20ms, sample memory/renderables/requests, continue until target polls reached, check that renderables and memory are flat (no leak). **Fuzz test**: Generate random message, write to temp log, call loadRoomLog, verify error message is specific (contains path and line), repeat 2000 times. **Replay**: Load room log, render each message via ChatView, breakpoint in debugger at interesting points.
