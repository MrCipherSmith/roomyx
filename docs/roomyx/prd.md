# roomyx — PRD

Version: 0.1.0

## Problem

Сегодня единственный интерфейс к startup-room — переписка в Telegram с диспетчером (этой сессией): оператор видит только то, что диспетчер решил пересказать, а не сырой диалог комнаты, не может заглянуть в то, что конкретный персонаж делает прямо сейчас, и не может подать команду комнате иначе как текстом, который диспетчер должен интерпретировать. Для быстро растущего использования (ресерч, ревью, техническая проработка — по словам оператора) это узкое горлышко: весь контроль и вся видимость идут через одну текстовую трубу.

## Goal

Дать оператору отдельный терминальный интерфейс (TUI), который показывает комнату как живой групповой чат — с возможностью открыть модалку любого агента и увидеть его работу отдельно — и позволяет подавать команды комнате напрямую (owner-injection), не проговаривая их прозой диспетчеру.

## Users

- **Оператор (altsay)** — основной пользователь; хочет смотреть на комнату как на живой чат и вмешиваться напрямую.
- **Оркестратор (Claude Code / Codex / `keryx shell` — какой запущен в конкретной сессии)** — технически поднимает MCP-сервер и пишет в него состояние комнаты; сам TUI не пишет.

## Requirements

### R1 — Единый провайдер на сессию
TUI не имеет собственного понятия "провайдер/модель" — он показывает то, что производит уже запущенный оркестратор. Смена провайдера = перезапуск сессии с другим оркестратором (Claude Code / Codex / keryx shell), не настройка внутри TUI.

### R2 — MCP-сервер как источник состояния
Оркестратор экспонирует состояние комнаты через MCP-сервер (не через сырой файл — решение принято в переписке с оператором в пользу второго варианта именно ради модалок и команд). Сервер живёт столько же, сколько сама комната.

### R3 — Общий чат-вид
TUI показывает основной поток комнаты как чат: кто говорит, что сказал, в реальном времени (через MCP-запросы состояния/дельты, не polling всего лога каждый раз).

### R4 — Модалка на агента
По каждому активному участнику — отдельный экран/модалка с его собственной активностью (минимум: его последние реплики и статус; максимум, если оркестратор это раскрывает — его текущие инструментальные вызовы/`thinking`, аналогично тому, что делает `keryx`'ный `mcp-inspector.ts` для MCP-трафика).

### R5 — Интерактивные команды владельца
TUI позволяет подать команду в комнату напрямую: vet o/constraint/добавить участника/изменить goal contract — то есть то, что сейчас идёт текстом в Telegram и интерпретируется диспетчером, здесь становится структурированной командой через MCP tool call.

### R6 — Ручной и автоматический запуск
Пользователь может запустить TUI вручную в отдельном терминале и подключиться к уже идущей комнате; либо оркестратор сам поднимает TUI как дочерний процесс при старте комнаты.

## Success Criteria

- Оператор может открыть TUI, увидеть живой чат текущей комнаты (той, что сейчас идёт в Telegram) без дублирования логики в диспетчере.
- Открытие модалки конкретного агента показывает то, что относится именно к нему, не ко всей комнате.
- Хотя бы одна интерактивная команда (например, veto) реально доходит от TUI до комнаты через MCP и логируется как решение owner'а, а не диспетчера.

## Risks

- **Два источника правды.** Если TUI получает право писать команды напрямую в комнату (R5), нужно явно решить, что единственный писатель append-only лога — по-прежнему оркестратор (дисциплина диспетчера из самого SKILL.md), а TUI лишь ОТПРАВЛЯЕТ команду через MCP tool, не пишет в лог сама — иначе теряется гарантия единственного писателя, на которой держится вся консистентность комнаты.
- **MCP как лишняя инфраструктура для узкой задачи.** Обсуждалось явно: простой файл был бы проще, но выбран MCP ради модалок/команд — если в разработке окажется, что нужный объём функциональности не оправдывает MCP-сервер, откат к файлу-логу остаётся дешёвой запасной опцией (R2 не завязан жёстко на конкретный транспорт в спецификации).
- **Живость модалки зависит от того, что оркестратор готов раскрыть.** Claude Code сегодня не отдаёт "внутренние мысли" субагента наружу как структурированный поток — модалка в v1, скорее всего, покажет только реплики и статус конкретного персонажа, не полную трассировку его рассуждений; это не блокер, но стоит заявить как реалистичный v1-предел, а не переобещать.

## Recommendation

Начинать с одного оркестратора (Claude Code, так как это то, что уже работает) — R2-R4 как MVP: MCP-сервер, отдающий чат и per-agent статус. R5 (команды) добавлять вторым шагом на том же MCP-контракте, не заранее. Codex/keryx shell как альтернативные оркестраторы — только после того, как контракт MCP-сервера стабилен на одном.
