# Project audit and review — 2026-09-27

Against `@mrciphersmith/roomyx@0.12.2`, commit `9fcec60`, `main`.

Nine independent passes over the whole of `src/` in path mode — not a diff.
Logic, architecture, security, concurrency, performance, clean code, testing
discipline, packaging and supply chain, plus a reconciliation of the existing
improvement backlog against the current code.

## Baseline

Green, with one caveat worth recording.

`bun run check` first failed with `eslint: command not found` — `node_modules`
was empty after two weeks idle. After `bun install`: eslint clean,
`tsc --noEmit` clean, **457 pass / 5 skip / 0 fail**, 2202 assertions, 36.7s
across 58 files. `bun audit`: zero vulnerabilities across 194 packages.

## Verdict

The project is in good shape, and the defects are not spread evenly — they
cluster in three places, and two of those three are the same root cause seen
from different angles.

What is genuinely strong, checked rather than assumed:

- **Release pipeline.** CI runs lint, types, unit and e2e plus `bun audit` on
  every PR. Release triggers on tag only, cross-checks tag against
  `package.json`, packs the tarball, installs it for real and smoke-tests the
  installed binary, then publishes via OIDC with provenance and no long-lived
  token. 29 git tags, 29 npm versions, zero drift.
- **Dependency direction, verified by a full import-graph walk.** No cycles.
  `log/` is a pure core touching only `node:fs` and `lockfile`. `server/` and
  `installer/` depend on it; `client/` and `cli.ts` are outermost. No layering
  inversion exists anywhere.
- **The no-build constraint is honoured.** No dev-only or out-of-`src` imports
  in shipped code. `npm pack --dry-run`: 146 files, 208 kB packed, 600 kB
  unpacked, nothing leaked.
- **The test suite is load-bearing, not merely large.** Sampled files assert
  behaviour against real servers and real renderers. The 5 skips are e2e behind
  `describe.skipIf`, run as a separate mandatory CI step. Ports use `--port 0`
  throughout; no fixed-sleep assertions.
- **The `test.failing` tripwire is sound and correctly applied** — one failing
  test pinning the upstream `@opentui/core` defect at three widths, plus a
  companion passing test at 120 so it cannot be dismissed as "wrapping is just
  broken".
- **The heavy comment style is worth keeping.** Asked directly, the clean-code
  pass judged it load-bearing regression documentation rather than noise:
  it records measured, non-obvious runtime behaviour a reader cannot rediscover
  from the code, and several comments exist specifically to stop a plausible
  future simplification from reintroducing a fixed bug. Moving it to `docs/`
  would disconnect the warning from the line it protects.
- **Security hygiene.** No `exec` with interpolation (argv-array `spawn`
  throughout), no prototype pollution, `export-name.ts` path traversal properly
  defended with both sanitisation and a containment check, DNS-rebinding and
  Origin guards present and correct on every response path, no hardcoded
  secrets, and no `postinstall` hook — that last one is a real strength and
  worth stating out loud.

## The three clusters

### 1. The writer lease is actively harmful

Found independently by the concurrency pass and the logic pass, each
reproducing it, and confirmed structurally here: `cli.ts:493` calls
`acquireWriterLease`, and `releaseWriterLease` is never called anywhere outside
`serve.ts:107`.

So `room append --take-over` acquires a lease in a process that exits
milliseconds later, and nothing releases or refreshes it. Every later append to
that log is then refused — for 30s as *"A writer is live — pid &lt;already
dead&gt;"*, and after that as *"a writer was in … pass `--take-over`"*, forever,
with each take-over writing a spurious `owner`/`status` line into the transcript
and re-arming the trap. `test/cli-room-ownership-e2e.test.ts` stops at the first
take-over, so the loop is untested.

Three separate signs the lease is the weakest invariant in the tree:

- `isPidAlive` exists in `registry.ts:255` and the lease path never calls it.
- `parseLease` reconstructs only `{token, pid, at}`, dropping `takenOverFrom` —
  so the first heartbeat, 5s after a take-over, erases the provenance that field
  exists to carry.
- Staleness collapses two different facts into one `false`, so a 30s laptop
  suspend is reported as *"another writer took it over"*, the heartbeat interval
  is cleared permanently, and the advice *"stop dispatching into this room"* is
  enforced by nothing.

`cli.ts` already records that the only expressible lease holder is an embedder
that `roomyx serve` never supplies. The lease therefore contributes zero safety
to the primary workflow — an agent appending by CLI — and one hard foot-gun.
**An inert guard that refuses legitimate writes is worse than no guard.**

The root cause sits one level up: D-01's single-writer rule lives entirely in
the `room append` handler (`cli.ts:383-497`). `log/write.ts` imports only
`lockfile`, `schema` and `types` — `appendMessages` takes the seq lock and never
consults a lease. Any second write path bypasses the invariant silently.

### 2. The log is re-read in full on every operation

Three passes arrived here independently, from three directions.

**Measured** (synthetic rooms, benchmark script): `loadRoomLog` costs 2.7 ms at
100 messages, 5.5 ms at 5,000, 32 ms at 10,000, 50 ms at 20,000 — while
extracting the tail delta actually needed stays under 0.6 ms at every size. It
is called unconditionally by `get_state`, `get_transcript`, `get_agent_detail`
and `get_agent_delta`, with no cache keyed on mtime or size, against clients
polling the transcript every second and state every three.

Worse on the write side: `nextSeq` re-reads and re-parses the entire log on
every single append, **inside the lock**, purely to learn the next number.
Measured 0.11 ms at 100 messages, 5.16 ms at 10,000, 46.89 ms at 20,000. That
makes populating a room O(n²), and it lengthens the critical section as the room
grows — so contention stops queueing and starts throwing, because
`lockfile.ts`'s 5s deadline is reached by waiters on a room that is merely
large.

The consequence is not only latency. The concurrency pass traced it further: a
concurrent `probeRoomState` runs on a 500 ms budget, times out while the server
is busy re-parsing, `checkRoomLiveness` returns `unknown`, and `room append`'s
guard receives `dispatched === undefined` — so an append is allowed into a room
whose dispatcher is alive and merely slow.

This is also **the one item still open in the improvement backlog** (R10's
memoisation half), which was deferred pending measurement. The measurement has
now been done.

### 3. The trust boundary on the MCP port

D-06 decided, deliberately, that there is no token in v1, on the argument that
*"the threat is limited to the operator's local machine, the same trust level as
the process that started the server"*. D-06a later amended it for browsers.

That argument holds for reading. It does not hold for the owner-command queue,
and this is an argued case to amend the decision rather than a claim that auth
was forgotten.

Reproduced live with plain `curl` and no credential: `initialize` succeeds,
`room.get_transcript` returns the full transcript, and
`room.post_owner_command` with `kind: "constraint"` and an instruction body
returns `status: queued` and comes straight back out of
`room.get_pending_owner_commands` — the queue the bundled skill instructs the
dispatcher agent to poll and obey.

So a local process at the same trust level does not merely read data. It gains
the ability to issue instructions to an agent that holds tools. D-06 enumerated
the actors but not this escalation; D-06a's guards stop a browser and, as it
says itself, do not stop a neighbouring process.

Proposed D-06b: mint a per-room bearer token at `serve()`, store it in the
registry entry — already the only place the port is written — and require it on
every request.

## Ranked work

Ordered by (impact × confidence) ÷ cost. Everything in P0 and P3 is small.

### P0 — cheap, confirmed, and currently biting

1. **Stop `room append` holding a writer lease.** Either release it on exit, or
   write only a tombstone invalidating the old token, and have `writerPresent`
   call `isPidAlive` before trusting a held lease. Triple-confirmed. Removes a
   permanent lockout of the primary workflow.
2. **Bound `seq` in the schema.** `src/log/schema.ts:91` is
   `z.number().int().min(1)` with no maximum. One line carrying
   `seq: 9007199254740991` passes validation and then every future append fails
   forever — the log is append-only and there is no repair command. Add
   `.max(2**48)` and have `nextSeq` refuse an out-of-range recorded seq rather
   than building on it. Reproduced end-to-end.
3. **Make the lock's wait deadline reach its own stale reclaim.**
   `lockfile.ts:54` waits 5s; `STALE_LOCK_MS` is 30s. A waiter can never survive
   long enough to reclaim a crashed holder's lock, so one `SIGKILL` mid-append
   fails every append for 30s with a timeout message that misstates the cause.
   Compute the deadline as `max(5000, STALE_LOCK_MS - lockAge)`.
4. **Don't lose the owner-command slot when a handler throws.**
   `server/index.ts:197` awaits `onOwnerCommand` with no `try/finally`, so a
   throwing handler leaves the entry pending forever; 32 of them wedge the queue
   behind a message that misdiagnoses the cause. Reproduced.
5. **Don't skip `exit()` when `cleanup()` throws.** `server/shutdown.ts:34`
   calls `cleanup()` inside `.finally()`; if it throws, `exit()` never runs and
   teardown ends as an unhandled rejection — measured `exits = 0`, with Bun then
   killing the process — leaving the room registered. `client/shutdown.ts:34`
   has the identical shape. Also exit non-zero when `close()` rejected, rather
   than always `exit(0)`.

### P1 — before promoting this publicly

6. **Add `SECURITY.md`.** There is none, in the root or `.github/`, and this
   tool writes into `~/.claude`, `~/.cursor`, `~/.codex` and `~/.grok` and
   registers MCP servers. A researcher has no private channel and will default
   to a public issue. Twenty lines.
7. **Write D-06b and mint a per-room token** (cluster 3 above).
8. **Refuse symlinks in `skill-sync`'s backup and write paths.**
   `copyFileSync(target, "${target}.bak")` and the subsequent `writeFileSync`
   both follow symlinks with no type check. Reproduced: a planted
   `SKILL.md.bak` symlink turned one `syncSkill({yes: true})` into an
   arbitrary-path write with attacker-chosen content. Reachable from an
   extracted skill archive that preserves symlinks — no code execution needed at
   plant time. `lstat` first; write with `O_NOFOLLOW`.

### P2 — the measured performance work: one change, three payoffs

9. **Cache the parsed log by `(mtimeMs, size)` and read the tail for `seq`.**
   This single change closes the only open backlog item, the measured 50 ms
   read ceiling, the O(n²) write cost, and the liveness-probe starvation that
   silently degrades the writer guard. Skip `foldEdits`' unconditional
   `[...messages].sort()` when the batch contains no edit-kind message.

### P3 — small, with measured or verified payoff

10. **Fix one import in `client/owner-prompt.ts`.** It runtime-imports
    `OWNER_COMMAND_KINDS` from `../server/index` — a pure re-export — dragging
    the whole MCP server SDK, zod and all four server tool modules into the TUI
    process for a four-element string array. Measured:
    `bun build src/client/owner-prompt.ts` = **465,800 bytes** versus
    **1,159 bytes** when built from `server/owner-queue.ts` directly.
11. **Fix the `.gitignore` the installer writes.** `IGNORE_LINES` uses
    `.roomyx/rooms/*.lock`, but room logs live in `.roomyx/rooms/logs/`.
    Verified with `git check-ignore`: the registry lock is ignored, every room
    lock is tracked. Use `.roomyx/rooms/**/*.lock`.
12. **Wire `scripts/soak.ts` into the release workflow.** `soak.ts`,
    `fuzz-log.ts` and `replay.ts` are referenced nowhere in `.github/` or the
    package scripts. `soak.ts`'s own header says it exists because *"the three
    worst defects this project shipped were all invisible to a unit test by
    construction"* — idle-client renderable exhaustion, unbounded session
    retention, reconnect storm. That class is currently guarded by nothing that
    runs automatically. It takes about two minutes.
13. **Validate the shape of the MCP config before rewriting it.**
    `ensureMcpServer` refuses unparseable JSON but casts anything parseable to
    `McpConfig`. Reproduced: `[1,2]` returns `ok: true, "registered"` and writes
    nothing; `{"mcpServers": "notanobject"}` spreads the string into
    `{"0":"n","1":"o",…}` over the operator's file. Validate with a small Zod
    schema and write temp-then-rename as `registry.ts` already does.
14. **Reject `limit: 0` on `room.get_transcript`.** `min(0)` in the input schema
    returns `{messages: [], has_more: true, next_seq: unchanged}`, so a caller
    following the documented cursor loop never terminates. Use `min(1)`.

### P4 — structural, larger, worth planning rather than doing now

15. **Move the single-writer decision out of `cli.ts` into the core.** A
    `canWrite(logPath, leasePath, {takeOver}) → Allowed | Refused | TookOver`
    beside the lease, required by `appendMessages`, with `cli.ts` rendering only
    the refusal. This is the root cause behind cluster 1, and it is what makes
    the invariant hold for an embedder too.
16. **Split `cli.ts`.** 980 lines holding four separable things — a dispatch
    framework, the envelope grammar, the writer policy, and 14 command
    presentations — and it calls `main()` at import, so none of it is
    importable. Six test files reach it only by spawning a subprocess. The
    project has already paid to extract twice for exactly this reason
    (`server/shutdown.ts` and `client/shutdown.ts` both say so in their own
    comments). Seam: `cli/dispatch.ts` plus `cli/commands/{room,rooms,install,mcp}.ts`,
    leaving a ~40-line composition root.
17. **Split `installer/` in two.** It holds install-time scaffolding (901 LOC)
    and runtime room coordination (558 LOC: registry, history,
    resolve-connection, room-tool). The second is the only reason the TUI has
    five import edges into a directory called `installer`. Move it to
    `src/rooms/`, and `writer-lease.ts` with it — it derives its path from the
    registry's directory, so it belongs there rather than at the root.
    `lockfile.ts` stays at the root; it is genuinely generic.
18. **Publish the core as a library.** `log/` is clean and dependency-free, and
    the README already tells embedders to use `serveManagement` — but
    `package.json` declares only `bin`, no `main`, `exports` or `types`, so they
    must deep-import an internal path that a rename silently breaks. Add an
    `exports` map. No build needed; `src/*.ts` already ships.
19. **Give the MCP wire contract a home.** `client/mcp-client.ts` type-imports
    `TranscriptPage` from a server *tool implementation* file and
    `OwnerCommandResult` from the server's composition root. A
    `src/protocol/room.ts` makes the protocol a nameable artifact and decouples
    the client from the server's file layout.
20. **Add idempotency to `appendMessages`.** A retried `room append` after a
    timeout duplicates the turn under fresh `seq`, and nothing in the envelope
    distinguishes the copy. An optional caller-supplied id, persisted and
    skipped inside the same lock section, closes it.
21. **Tolerate a torn tail on read.** Readers take no lock and treat a final
    line without a trailing newline as fatal for the entire log, so one
    in-flight append makes `get_state`, `get_transcript` and `serve` startup all
    fail at once while every earlier line is intact. Drop a final unterminated
    line; cap `body` length so one line cannot span a multi-syscall write.

## A disagreement between reviewers, recorded

The concurrency pass reported `Math.max(...seqs)` in `nextSeq` as a major
finding, claiming a `RangeError` above roughly 125,000 messages. The logic pass
measured Bun's actual spread limit at approximately 1,000,000 elements and
deliberately did not report it as unreachable for a room log.

The construct is real — `write.ts:77` and `store.ts:148`. The threshold claim
was wrong. Replacing both spreads with `reduce` is still worth doing, as hygiene
rather than as risk.

This is recorded because the first number was relayed to the owner as verified
before the second pass returned. What had been verified was that the construct
exists, not the threshold at which it fails.
